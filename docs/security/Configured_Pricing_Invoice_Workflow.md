# Configured pricing and manual invoice workflow

Baseline e4c4d90e7cab39915f6a01ab3895b49ce729c329; backend-only finite batch, existing dist preserved.

## Plan and boundaries

1. Independently approved immutable issuing-entity billing/calculation versions: explicitly enabled three-character currencies, precision/rounding, recorded-weight/bucket rules, included services, separate charges/discounts/tax order and treatment, eligible order states and manual-only billing. No metadata, tax, precision or production defaults. Explicit capabilities, fresh selected-company scope, exact version/content and different maker/checker. Existing immutable tariff configuration supplies base rate authority.
2. Explicit durable bill-to instruction: authorized master customer and order, recorded evidence/reason; never infer payer from recipient, customer userId or COD. Immutable order-price proposals/standard acceptance and independently approved exceptions/revisions, bound to original order/entity/payer/tariff/policy/calculation inputs and exact components. Context-bound request identities, shared order locks and atomic current acceptance pointers.
3. Manual single-order invoice from accepted snapshot only; issuer/payer/currency/total derive from durable authority. Existing Invoice remains the billing document; additive source/receipt/outbox links. Atomic numbering, receipt/audit/event facts, fresh retry authorization, no automatic accounting/FX. Existing issued history cannot be silently adopted or rewritten.
4. Focused pure calculation/HTTP and actual disposable PostgreSQL authorization, approval, source-change, retry/concurrency/rollback scenarios against the final additive migration chain. Review and local milestone commits; update current dashboard and stop.

Supported calculation modes are implementation capabilities, not policy defaults: publishers must explicitly select supported arithmetic and provide each rate/treatment/order/inclusion/eligibility value. Reject unsupported modes, duplicate service keys, unknown fields and excess limits. Historical unowned settings/estimates remain unaccepted. Automatic/delivery/periodic issuance, consolidation, FX, accounting, voucher/promotion engines, refunds and real-provider recovery remain outside this batch.

Production requires explicit approved TransAsia configuration and deliberate safe permissions/provisioning. Synthetic fixture currency/rates/rounding/tax/order eligibility/payer evidence establish only test behavior. Roll out additive schema before writers; stop incompatible old writers, preserve immutable evidence on rollback and recontain dependent entrypoints. No existing database/service access, client change or dependency addition.

## Enforced workflow and contracts

Every new operation checks fresh active tenant/company membership, explicit selected-company scope, an active owned issuing entity and its dedicated permission. Order and customer/object scopes remain separate requirements. Authority repeats after company-lock waits and parent-order locking; the final authorization-read/commit revocation window is not eliminated. Permission definitions have no automatic grants.

Under /api/pricing:

| Endpoint | Strict request fields and permission |
|---|---|
| POST /billing-policies | operationId, reason, content; billing.policies.propose. Entity derives from selected company. |
| GET /billing-policies/:id | pricing.read; minimal owned configuration/version/decision projection. |
| POST /billing-policies/decision | versionId, contentHash, decision approved/rejected, operationId, reason; billing.policies.approve, different user from maker, exact current proposal. Terminal immutable decision; newer approved revision changes selection without rewriting history. Matching old retry never rewinds it. |
| POST /orders/:id/bill-to | payerCustomerEntityId, evidence, operationId, reason; billing.payers.bind and scoped customer access. Immutable instruction, no replacement after binding/invoicing. |
| POST /orders/:id/price-acceptance | operationId, reason; pricing.orders.accept. Standard no-discount proposal accepts atomically; discounted proposal and every revision return approval_required without changing authority. |
| POST /orders/:id/price-approval | snapshotId, contentHash, operationId, reason; pricing.orders.approve, different user from maker, exact current source/input hash and previous acceptance. No proposal rejection/cancellation tool in this batch. |

Existing POST /api/invoices/orders/:orderId/issue adds the strict body {operationId, priceApprovalId, reason}. Accepted price supplies payer, issuer, currency, components and total; accepted policy supplies order eligibility, prefix and due days. No caller amount, currency, paid state or dueAt. Response amount stays a decimal string with four places; additive billing metadata (priceApprovalId, policyVersionId, payerCustomerEntityId, legalEntityId) also appears on authorized list/order-detail reads. Existing customerId/customerEntityId remain order-party compatibility fields, not payer authority. Legacy owned issued-invoice reads/retries remain supported; legacy new issuance still rejects INVOICE_PRICING_ACCEPTANCE_REQUIRED. New intent cannot adopt an unaccepted invoice.

Bill-to authority is an explicit authorized recorded instruction backed by server-owned order/entity/customer relationships and bounded evidence reference. It is not independent verification of customer consent or a legal agreement. Payer may differ from recipient/customer user and merchant COD beneficiary. COD amount never enters service-price components.

Each action requires a persisted client-generated UUID operationId and normalized immutable payload/reason. Matching retries reauthorize current context and payer access before returning the original result; conflicting content/context rejects. Database uniqueness, company advisory serialization, parent-order locks and conditional pointer updates protect covered duplicates and competing revisions. Preserve original IDs across uncertain responses. Company serialization is deliberately coarse; transactions have 2s lock, 5s statement, 2s acquisition and 10s transaction bounds, without network work. Receipts do not grant access.

## Explicit production configuration, not defaults

Publishers must supply every supported choice:

- Currency: any three uppercase letters, precision 0..4 (current Invoice storage limit), rounding HALF_UP/HALF_EVEN/DOWN/UP, roundingStage each_component. Explicit approval enables that company/entity currency. This is not a verified global currency registry or provider minor-unit contract.
- Weight: recorded_order_kg/as_recorded only. Zone source structured_address_cities, explicit city/country pairs, zone, domestic/international coverage and transport mode. Owned master customer and both owned structured addresses are needed for financial acceptance. Free-text logistics remains available but cannot establish an invoiceable route. Existing Float weight is a non-money measurement canonicalized as a decimal string; Float service/cost estimates never establish money authority. Volumetric/fractional-weight rules and linear/transit pricing remain unsupported.
- Tariff: FIXED_LANE/bucket, explicit includedServices. Selection uses published owned active snapshots matching service/currency/coverage/mode. Customer/default/priority/creation precedence is retained. Template-specific plans require owned active template and actual order-leg linkage. Top candidate requires exactly one zone/weight bucket; no lower-plan substitution. Included service and fee codes cannot overlap; accurately declaring tariff inclusions is an approved configuration responsibility.
- Fees: explicit flat per-order service/amount strings, applied once; not conditional service eligibility or promotions. Discounts: explicit ordered code/type flat-or-percent/value strings, applied sequentially to running subtotal (stored discount amount is a positive reduction, subtracted in the calculation); every discounted acceptance requires a different approver. calculationOrder explicitly selects discount_then_tax or tax_then_discount. Positive bounded total, 30 fees, 10 discounts, 100 city mappings/candidate plans; monetary Numbers, malformed/negative base strings and unsupported modes reject.
- Tax: explicit exclusive_percent rate/authorityReference, or exempt/not_applicable with authorityReference. Missing tax is not zero or exemption. Reference text is approved instruction, not tax-law certification. No real VAT rate inferred.
- Billing: manual mode, explicit eligibleOrderStates (cancelled unsupported), dueDays 0..365 and numberPrefix. Due days are elapsed server-time days. One order per invoice. Automatic/delivery/periodic triggers and consolidation remain unavailable.

Before real TransAsia use, deliberately provision owned records, active entity, master addresses/customer, scoped makers/checkers and payer instructions; independently approve actual tariff inclusions, flat per-order fees/discount sequence/tax treatment, precision/rounding, city/country zones, weight basis, eligible states and due/numbering policy. UZS is intended initial currency but no production settings are provisioned or approved. Synthetic ZZ/VAT/fee/payer examples prove test behavior only.

The existing Invoice fxRate contract is a base conversion: entity.baseCurrency must equal accepted selling currency, otherwise BILLING_BASE_CURRENCY_FX_POLICY_REQUIRED. Configured foreign-base prices can be accepted, but issuance remains contained rather than fabricating identity FX. Payment/Stripe minor-unit support is separately restricted; this batch does not make arbitrary configured invoice currencies/precision compatible with providers.

## History, rollout and gaps

Three additive migrations introduce immutable BillingPolicyVersion/Decision, OrderBillTo, OrderPriceSnapshot/Approval, current order acceptance pointer, Invoice source links, InvoiceIssuanceReceipt and BillingInvoiceOutbox. Compound constraints bind tenant/company/entity/order/payer/policy/money and actor bridges. Independent-maker checks and UPDATE/DELETE/TRUNCATE protection preserve new histories. Pointer cannot clear/rewind/change after invoicing. Linked invoice financial/source/party/FX/issuance fields cannot be rewritten; issued-to-paid remains permitted. Cancellation/credit/reissue needs a separate controlled correction contract. No historical adoption, backfill or posted-record edits.

Invoice, number, receipt, audit and source-bound invoice.issued fact commit atomically. BillingInvoiceOutbox is held_no_accounting_authority, immutable, with no publisher/consumer. It records a fact, not delivered accounting/provider success; existing accepted finance publishers do not consume it. Accounting mappings, period/rule/configuration acceptance, FX, refunds and provider recovery remain contained. No exactly-once external claim.

Deploy all three additive migrations before compatible generated clients/writers; stop incompatible old pricing/invoice writers and unapproved finance publishers before enabling permissions. Preserve constraints/evidence on rollback or disable affected operations; never restore unscoped writes. Nullable legacy links do not establish full isolation or certify historical records/NOT VALID constraints. Production migration execution is not authorized here. Deferred clients need durable operation IDs, payer/configuration/approval UI and pending/409 handling. No source-to-dist, Redis, real provider/S3/device, dependency or production-readiness certification.
