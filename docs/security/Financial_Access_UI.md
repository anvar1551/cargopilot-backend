## Implemented contracts and compatibility

New GET /api/auth/company-financial-access?view=ceiling|recipients|proposals|grants&kind=proposer|checker&limit=1..50&cursor=... returns private/no-store snapshots. Ceiling includes only current accepted actor authority, the active owned legal entity and exact registry profiles/keys. Other pages are bounded to selected tenant/company/entity/kind/view and actor membership; candidate filtering can produce empty pages with a next cursor. No credentials, email addresses, token/hash/permit/operator material or unrelated role/scope details are returned. Fresh selected context, explicit company scope, current membership eligibility, accepted authority/action and owned active entity are required. Reads take no business/advisory/row locks and perform no writes. All mutations retain existing independent authorization/locking/receipts; visibility is not authorization. Snapshots may become stale, including proposer authority or recipient eligibility; mutation revalidation remains authoritative.

Frontend /dashboard/manager/financial-access and permission-aware navigation present named eligible existing recipients, owned entities, accepted ceiling/profile keys, immutable proposal/fingerprint/previous-acceptance inspection and managed access. Proposer/checker views are separate; pending grants confer no access. Replacement is another independently accepted proposal. Revocation affects only workflow-managed access. No manual identifier fallback, role-name authority, operational/driver delegation fallback or automatic prerequisite creation.

Propose/accept/revoke intents persist once per API origin + user/tenant/selected-membership context and mutation kind before sending, with read-back and Web Locks. Requests retain operationId, normalized original payload and (for accept) inspected immutable target/entity/profiles locally; that client-only snapshot is stripped from the unchanged API request. Explicit retries send the original intent; refreshed selectors cannot replace it. Late auth-epoch/context responses cannot confirm or write the previous intent. Unknown/ambiguous outcomes remain uncertain, not successful. Only confirmed actions can be finished to start another intent; unconfirmed intents have no abandon/reconciliation contract. Missing Web Locks/storage fails closed. Existing finance screens are preserved.

Backend-first rollout: deploy the read contract before enabling the workspace. No schema, migration, dependency, profile, permission, ceiling or financial mutation change. Entity setup and owner appointment must already be independently completed; recipients must have eligible existing selected-company membership and scope. Driver memberships remain excluded. Access acceptance/revocation requires recipient fresh login through existing session revocation. No invitation/token/password input or secret persistence in this workspace.
