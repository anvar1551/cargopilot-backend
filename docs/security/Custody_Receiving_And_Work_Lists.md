## Receiving contract

POST `/api/orders/:id/custody` preserves its receipt response and existing required operationId/action/expectedEventId/exact expectedUpdatedAt/whole parcelIds/warehouseId. Intake and receive alone accept optional `outgoingDriverReason`: trim-normalized 10..500 characters, no control characters. It becomes required when the recorded outgoing CompanyMembership or TenantMembership is currently suspended; absence rejects 400 before business writes. Other actions reject this field. The reason is part of normalized immutable intent, so changing it after confirmation is conflicting reuse (409); ambiguous retries must retain the original ID/content/reason. A matching already-confirmed receiving retry returns its original audit/result after fresh receiving authorization, even if outgoing status changed later; it does not rewrite the observation or manufacture new evidence.

Current schema has active/invited/suspended membership states, not a separate revoked enum. Suspension represents disabled membership; deleted/missing or inconsistent bridges remain rejected. The existing pickup offer or accepted transport must have recorded outgoing actor/user/company-membership agreement; its TenantMembership must still match that original selection/tenant/user. Receipt no longer depends on outgoing telemetry/action permissions, driver type or login remaining active. No driver action is authorized by this exception: fresh active eligibility remains mandatory for all their actions/retries. Receiving requires its own fresh active selection, dedicated capability and exact durable destination warehouse scope. Current Order/parcel/leg/expected state and existing company/tenant ownership guards stay. Cancelled/conflicting/unaccepted legs/bookings reject; there is no cancellation/replacement override.

The new receipt's immutable beforeState.outgoing stores original predecessor event/user/CM/TM, observed CM/TM statuses, suspended boolean and normalized reason. The original outgoing journal record remains unchanged; current custody moves to the receiving warehouse. The receipt row is both audit and original operation evidence, committed with manifest/Order/leg/Tracking/notifications/analytics. No status reactivation, impersonation, provider/storage call or history overwrite. Status is a server-side observation during the existing transaction, not a claim to remove every read-to-commit revocation race.

## Restricted discovery contract

GET `/api/orders/custody-work?kind=warehouse|driver&limit=25&cursor=...` returns `{items,nextCursor}`. kind is required; limit is integer 1..50 (default 25); unknown filters and invalid/cross-context cursors reject 400. Each item has only orderId, orderNumber, status, expectedUpdatedAt (ISO), expectedEventId, phase, currentWarehouseId, destinationWarehouseId and legId. No amounts, people/contact names, proof/file URLs, credentials, normalized intents or audit payloads. Use the existing custody snapshot for complete bounded parcel IDs; the list does not supply mutation authority or replace expected-state revalidation.

Warehouse lists require shipment.view, appropriate intake/receive/dispatch/last-mile-offer capabilities and explicit owned warehouse scopes (at most 100 distinct scope IDs). Company scope alone is insufficient. Incoming pickup offers/accepted transfers match exactly their destination; held actionable warehouse work matches latest warehouse phase/currentWarehouseId. Driver lists require shipment.view, telemetry, current local/linehaul eligibility and the phase-specific custody capability; records match exact selected CM plus user. They include nominated transfers/last-mile offers and currently held pickup/transport/last-mile custody, excluding delivered and stale older nominations. Unaccepted transport is visible to its nominated driver for acceptance, never as receivable destination work. Inconsistent/cancelled current leg/booking sources are excluded; lists never fabricate external success.

Latest journal per owned order is selected in PostgreSQL, with tenant/owning-company and non-conflicting assignment predicates. No in-memory global scan or user-global room/query fallback. UUID orderId ascending keyset pagination fetches at most limit+1 records. Cursor binds user/tenant/TM/company/CM, kind, page size, relevant warehouse scopes and current permissions. It is a validated opaque seek hint, not a signed authorization capability; forging a seek position cannot expand the independently rebuilt database ownership filters. Context/scope/permission changes require restarting pagination. Live state can change between pages; no fixed snapshot or whole-batch atomicity is claimed. Query/lock deadlines are 5s/2s and transaction 10s, with maxWait 2s; bounded returned rows are not a fixed physical scan-row guarantee. Existing latest-journal index is reused; production volume/query-plan verification remains outstanding.
