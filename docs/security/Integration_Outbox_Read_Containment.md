# Selected integration outbox metadata reads

Current enforced application behavior: list and delivery-attempt entry points reload the exact selected tenant/company membership, require `integration.outbox.read` and an explicit selected company scope. Other memberships and `policy.override` do not broaden this boundary. Optional company filters are equality assertions. Missing bridges, inactive context and missing permission/scope fail closed. Metadata access is company-wide, not authorization to view an order payload or replay a business operation.

The query repeats active company/tenant ownership and a server-loaded provider tuple (ID, company, domain, code, environment). A missing/foreign/conflicting provider excludes the outbox from both rows and counts. Populated order ownership must resolve to the same tenant and owning company; partial bridges are excluded. An entirely absent order bridge remains eligible only for company-owned integration metadata, not order content or execution. No tenant mapping, historical certification or new database constraint is claimed.

At most 100 matching provider configurations expand into query alternatives. A 101st returns `409 INTEGRATION_READ_CAPACITY`, never a truncated total or global fallback. List callers can narrow domain/provider-code filters; attempt reads cannot be served for a company exceeding that cap until a bounded joined-query implementation replaces tuple expansion. Each tuple is repeated in the actual provider relation predicate so a configuration change cannot match stale tuple authority. No provider status requirement is added to historical metadata: paused/disabled providers remain readable under an active owning company/tenant.

List/count use the identical predicate. Pagination permits integer pages 1–10000, limits 1–100; attempts limit 1–200 and repeat parent ownership in the child query. Ordering has an ID tie-breaker. Fresh membership verification precedes protected reads; concurrent revocation after that check remains a timing boundary, not demonstrated immediate revocation. The ordinary read transaction does not promise snapshot-stable totals during concurrent writes.

Compatibility: list `{items,total,page,limit}` and attempt arrays remain. Error statuses are sanitized. Raw payloads, request/response JSON, error text, provider request identifiers, idempotency keys and aggregate/event/operation identifiers are not queried or exposed by these metadata permissions. Existing sensitive/free-text keys return `null`; clients that displayed them must handle unavailable detail. Nested provider and attempt projections are explicit. Clients remain deferred/unverified. Replay/retry-now remain unavailable under the independently documented recovery containment; automatic worker policy is unchanged.

Evidence: focused mocked predicate/projection/authorization tests and Fastify injection tests exercise the actual service exports/routes without databases, DNS, storage or providers. Query syntax is checked against installed Prisma types with no-emit TypeScript. No PostgreSQL query execution, concurrency, historical data, infrastructure or provider transport evidence is claimed by these tests. No schema or writes changed, so no new migration/client generation or database run was required for this slice. Existing callback PostgreSQL deadline/deduplication evidence applies only to its unchanged code.

Next boundaries: webhook/canonical event reads still need their own source graph and selected-context predicates; non-financial immutable configuration auditing, secret-pointer/version constraints and routing remain technically unfinished. All finance approval/accounting/FX, nullable historical certification, recovery, tenant cutover, RLS and infrastructure release gates remain open.
