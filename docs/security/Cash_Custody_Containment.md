## Current enforced behavior in this slice

- Every service entry reloads active user/tenant/company membership context and permission with `requireFresh`; mutations reload again after acquiring the order lock. The established order-scope builder remains mandatory, with an additional exact selected owning-company condition for cash. Tenant equality cannot replace company/customer/warehouse/driver/object scope. Tenant-null orders are inaccessible. Caller actor fields cannot supply permissions or warehouse authority.
- Collection requires `shipment.update`, assigned actor or explicit scoped current warehouse, `NOT_PAID`, a positive server obligation, explicit currency and complete consistent FX/base-currency snapshots matching the active authoritative finance legal entity. Only assigned/pickup-in-progress/picked-up/at-warehouse/in-transit/out-for-delivery/delivered orders permit these covered operations. Partial, missing and incompatible states fail closed; no amount correction or partial collection is implemented.
- Collection is expected -> held; handoff is held -> a different authorized custodian; settlement is held -> finance. Handoff requires the current custodian, not a manager override. Target driver must be the assigned driver with an active matching company/tenant bridge; warehouses require explicit scope and tenant ownership. Warehouses are tenant-owned in the current model, not inferred legal entities. Settlement requires `finance.settleCash`, relevant order/custody scope, and an actor distinct from collector, last custody maker and current person holder.
- A matching tenant/company-scoped operation identity and fingerprint returns its stored response snapshot without another event. Conflicting reuse fails. Order and custody row locks serialize initialization and incompatible transitions. Handoff/settlement require the latest `expectedEventId`; a new key cannot replay stale custody. The unique database operation key and event identity backstop concurrent writes. Transactions have bounded wait/execution settings; operational pool/lock tuning remains to be verified.
- `CashCustodyOperation` has mandatory tenant/company/order, collection/event, actor/membership, exact `Decimal(20,4)` amount, currency, fingerprint, action and result. Compound foreign keys prove selected order ownership, same-order collection, same-collection event and matching actor membership context. SQL additionally checks positive money, currency/key/fingerprint shape and operation type. FK ownership equality does not prove legal classification or business permissions.
- Cash state, order paid flag, immutable event, receipt and two durable analytics/finance events commit together. No storage, provider, direct realtime notification or network publication is performed by the mutation. Former direct driver cash notifications and route invalidations are suppressed; committed outbox invalidations retain existing event types. Actual external delivery is unverified and is not exactly-once.
- Online service-charge reconciliation uses the same order/custody lock ordering and refuses to overwrite held/cancelled custody. Cash service-charge collection rejects CARD/TRANSFER obligations. The existing verified online-payment flow remains otherwise outside this slice.
- Queue list/count/summary require fresh context and the same selected-company order scope. Unowned parents and custodians without an active matching bridge, or foreign holder warehouses, are hidden. Summary refuses scopes above 1,000 orders instead of issuing an unbounded query. Its legacy float totals/mixed-currency shape are informational, not monetary settlement authority.

## API and migration compatibility

Routes and success/bulk envelopes remain. Every mutation requires a caller-generated stable `operationId` (8–100 permitted characters); each bulk item carries its own key. Handoff/settlement additionally require `expectedEventId` from current custody. Collection accepts omitted/null `amount` only; any supplied monetary value, paid state, tenant/company/collection authority or unknown field is rejected. Bulk input is bounded before parsing. Independent items retain partial success (207); a failed item commits no mutation/outbox, while earlier successful items remain committed.

Mutation `order` is now a minimal stored operation snapshot, not a full order-detail object: identifiers/status/paid flags and the affected cash collection with its event ID. Monetary values there are decimal strings. Matching retries can return a snapshot preceding later custody changes; obtain current state through authorized reads. Current frontend and driver calls send no operation keys or expected custody event IDs and therefore are incompatible with these mutation contracts. They require a separate client slice; offline retries must keep the same key and selected identity/context. No queued replay under another membership is authorized.

Apply migration `20261001120000_cash_custody_authority` and generate the client before enabling reviewed source. New receipts restrict removal/movement of referenced records, including membership deletion; revocation by status remains possible. Existing expected rows are checked against the server obligation; existing held rows without a receipt remain contained. No backfill, historical acceptance or ownership assignment occurred. Rollback must retain enforcement or disable affected cash mutations; do not restore the former unscoped handlers. Rolling operation with an older mutable cash implementation is not safe.
