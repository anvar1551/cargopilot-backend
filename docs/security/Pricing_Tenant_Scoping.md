# Pricing tenant scoping

## Current enforced behavior

Tariff-plan list, detail, creation, update, deletion, quote and quote-options paths now require a current authenticated tenant session, the selected company membership, the relevant pricing or shipment permission, and an exact company scope. The repository reloads that access snapshot before querying pricing data. Missing, stale or inconsistent context fails closed.

New tariff plans derive `tenantId` and `companyId` from that verified context. A request cannot choose ownership fields. An optional customer reference must pass the tenant-scoped customer access control, and an optional route template must belong to the selected company whose organization belongs to the selected tenant. The database enforces these equalities for populated ownership through compound foreign keys.

Tariff selection is restricted to the verified tenant and selected company. Existing customer-specific, default-plan and priority precedence remains unchanged inside that boundary. A request `companyId` is treated only as a selector assertion and is rejected if it differs from the selected session company. The order creation path uses the same selection rules with `shipment.create`; its customer/address containment remains active.

Legacy tariff plans with null ownership are not inferred or assigned. Tenant-facing plan and quote queries exclude them. The additive presence check permits only both ownership columns null or both populated. When both are null, optional customer or route-template references may still be populated and receive only their legacy existence checks; no tenant or company equality is established for such a row.

Currency normalization, supported-currency validation, FX behavior and the existing pricing calculations are unchanged.

## API and consumer compatibility

The `/pricing/tariff-plans`, `/pricing/quote` and `/pricing/quote-options` response shapes remain unchanged. These endpoints now require a fully provisioned tenant-bound session and selected-company scope. A client-supplied `companyId` on quote requests must match the session selection. Tariff-plan write bodies are strict and reject unknown ownership fields.

Order creation no longer supplies company identity to the quote repository; it passes the authenticated session and the repository derives the company. CSV preview and execution now use that same preparation path. Preview validates every syntactically valid row against the current tenant, selected company, membership, scope and tariff rules without writing. Execution resolves the same context and pricing again immediately before each row is created. Optional `originCity`, origin/destination country and transport-mode columns were added to the template so imports can supply the route inputs used by the existing calculator. No frontend or driver repository was changed in this slice.

CSV columns or nested inputs that attempt to select tariff/route configuration, service charges, payment amounts, paid state or workflow status are rejected. The existing customer/address master-reference containment remains active. A cash/manual-payment row may retain a null charge when no rule quote exists, matching normal creation; an online-payment row is rejected when an authoritative quote is unavailable. No fallback plan is substituted.

Import execution remains sequential and is not an all-or-nothing transaction. Preview prevents currently invalid rows from starting the batch, but a membership/configuration change or operational failure during execution can leave earlier rows committed. Pricing-component seeding remains best effort after each committed order, and label queue/generation retains its previous queue, asynchronous or synchronous failure behavior. Durable import idempotency and recovery remain separate blockers.

## Remaining boundaries

Source establishes that `PricingRegion`, `ZoneMatrixEntry`, `DeliverySlaRule` and `OperationalSlaPolicy` have no tenant/company ownership and are consumed globally by quote or SLA resolution. It does not establish whether that is an approved shared-reference-data design. Because an ordinary pricing administrator could change other tenants' quote or SLA behavior, their create/update/delete/upsert paths and the global SLA backfill now return 503 before database work. Read/resolution paths remain available; reading the SLA policy no longer creates a missing global row and returns 503 until a separately authorized initialization process exists. The product decision and ownership migration needed to restore mutation are unresolved. Route templates remain company-owned without their own direct `tenantId`; their tenant is established through the owning organization relation.

Nullable tariff ownership is expansion behavior. Null `tenantId` plus null `companyId` bypasses the new compound ownership checks, whether or not optional customer or route-template references are populated, although application queries hide those rows. A partially populated tenant/company pair is rejected. A later audited mapping/contract migration must address or remove unowned rows and make ownership mandatory. PostgreSQL row-level security remains deferred defense in depth. Runtime repository scoping and populated-row constraints do not establish complete tenant isolation across order imports, all pricing configuration, caches, jobs or reports.

The applied-migration-to-Prisma comparison is not globally clean. Comparing the committed baseline source with an isolated current migrated database attributes the default-expression, finance timestamp/index-name and customer default-address relation differences to unchanged baseline files. This slice intentionally retains the older single-column tariff customer and route-template foreign keys as compatibility protection for fully unowned legacy tariff rows; Prisma models the stronger compound relations and therefore reports those older constraints as extra. The initially detected new tariff index-name mismatch was corrected with an explicit Prisma map. The current isolated comparison reports no other pricing-specific difference, and `git diff HEAD` confirms this slice did not alter the reported UUID defaults. The new migration was separately applied from an empty database and its populated ownership behavior was exercised directly in PostgreSQL.
