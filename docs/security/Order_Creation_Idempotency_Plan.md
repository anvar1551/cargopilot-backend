# Durable order/import creation: bounded execution plan

Status: planned, not implemented. Baseline diagnostic checkpoint `0a4d0ef23b2c3f6ad22abcb973dd3eedd1676a94`. No schema, API or persistence change is made by this plan. Clients remain deferred.

## Confirmed uncovered invariant

Only two production callers invoke `createOrder`: `write/create-order.ts` and `import/order-import.ts`. Both currently create an order in `repo/order-write.repo.ts`'s transaction without a durable request identity. Atomic `Counter.upsert` protects order numbering, not duplicate creation. The order, parcels, initial cash records, tracking and analytics outbox commit together; pricing seed, labels and normal-path carrier auto-booking run afterward. Retrying an uncertain request can therefore create another order and repeat external work.

`prepareAuthorizedOrderCreation` mutates the mapped payload with current tariff service charge/currency. Fingerprinting that mutated payload would falsely conflict after a tariff change. Matching receipts must be checked after fresh creation authorization but before recomputing the quote. Quotes remain operational estimates; this task cannot approve invoice pricing, accounting or FX policy.

Import preview validates all rows before execution, then execution commits sequential rows and runs best-effort pricing and label work. A later failure leaves earlier rows committed. A row-only receipt is insufficient: changed content in an as-yet-uncreated row must not become a new intent under an existing batch ID.

## Proposed contract and implementation ordering

1. Require client-generated UUID `operationId` for normal creation and import confirmation; preview remains non-mutating and needs no ID. Missing ID rejects before business writes; never generate a replacement on the server. The existing nested payment idempotency key is not an order or batch identity. Document the breaking contract for deferred clients, keeping current response fields where possible. Imports retain the same batch ID, exact normalized row sequence and payload across retries.
2. Capture a bounded, canonical, versioned normalized **pre-quote** creation intent from `mapCreateOrderDtoToRepoPayload`. Use reviewed explicit fields, stable object-key ordering, ordered parcels/rows and SHA-256. Include operation kind and selected user/tenant/tenant-membership/company-membership/company identity in conflict comparison. Do not store/log raw addresses, phone numbers or exception objects in the receipt. Existing exact-money and financial authority containment must remain; this is not a Float-to-Decimal migration.
3. Add an immutable `OrderCreationIntent` header with non-null tenant/company/user/bridge fields, operation ID, normal/import kind, fingerprint/version, row count and server time. Use unique `(tenantId, operationId)` plus existing compound membership targets. Add `OrderCreationReceipt` with header/ordinal and authoritative order/tenant/company compound relationship; unique `(intentId, ordinal)` and order identity. Normal creation has exactly ordinal 0; import uses the immutable ordered row sequence. No historical receipt inference or default identity.
4. Bind acceptance under a tenant/operation transaction advisory lock, fresh selected membership/creation permission/explicit company scope, and uniqueness. Matching header retries retain exact context and hash; conflicting reuse denies without new business writes. Header acceptance for imports commits before per-row execution, preserving partial success; all structural/authority-invalid input must reject before acceptance. Never hold a transaction around provider/storage work. Add suitable append-only header/receipt guards and explicit row-kind/ordinal/completeness constraints; do not edit historical migrations.
5. Refactor the existing repository transaction body into a transaction-local creator rather than nesting transactions. Normal intent+receipt+order+parcels/cash/tracking/outbox commit atomically. Each import row locks the accepted header/ordinal, reloads fresh eligibility, and commits receipt+order and current related writes atomically. Matching receipts return the existing owned order only after fresh creation permission/company scope and exact selected ownership checks. Do not add a generic optional bypass to the repository contract; audit the two actual callers and relevant tests.
6. Return an internal replay flag and skip all post-creation pricing/carrier/label effects for confirmed receipt retries. Recheck current order authorization before exposing an existing result; stored receipts never grant access. Keep public order fields unchanged where safe; distinguish durable order confirmation from unconfirmed downstream work. A crash after order commit but before downstream work leaves explicit recovery work, not permission to replay uncertain provider operations. Import continues unconfirmed rows only under its identical accepted header and fresh context; does not replay effects for completed rows or blanket-transaction the batch.

Exact affected files: `prisma/models/orders.prisma`, `identity-access.prisma` and `tenancy.prisma` for receipt/header inverse relations (plus organizations only if a direct owner relation is necessary after checking existing compound targets); one new additive migration; `domain/orderCreate.mapper.ts`/new bounded intent helper; `repo/order-write.repo.ts`; `write/create-order.ts`; `import/order-import.ts`; their two transport route files; focused creation/import tests and one guarded PostgreSQL integration file using the existing synthetic adapter; this plan and backlog. Inspect exact relation targets before adding any unique index; do not duplicate existing ones.

## Observable completion and validation

- Fresh authorized normal creation returns one order; identical normalized retry returns that order without a new number, cash/tracking/analytics event, pricing seed, carrier/provider call or label job.
- Same tenant/operation with different payload, kind, row sequence, user or selected company/membership rejects. Foreign/missing/revoked context and ownership/status/master-reference manipulation reject without business effects, including before returning receipts.
- Import confirms each row at most once; interrupted identical retries retain previously confirmed rows and create only remaining rows. Changed later rows conflict against the accepted header. Preserve existing partial-success/best-effort seed behavior and document unavailable downstream reconciliation.
- Actual disposable PostgreSQL cases invoke the real implementation: concurrent identical normal and import-row requests produce one order/receipt/outbox result; conflicting concurrent requests admit one intent; failure between order and receipt/outbox rolls back all related state; fresh revoked authorization denies existing receipts. Test populated foreign membership/order constraints and updates, append-only header/receipt protection, and zero-write conflicts.
- Mock provider/storage/job evidence proves suppression, not transport guarantees. Full committed migration chain plus the new migration runs only on one new labeled cached-image `--pull never`, loopback synthetic PostgreSQL resource with owned tmpfs and verified cleanup. Run offline schema validation and no-emit checking after relevant changes. Use affected tests, not the unchanged entire audit/milestone.

## Migration / compatibility / recovery

Additive empty tables only; no existing rows backfilled or rewritten. Nullable business ownership remains transitional. The API cutover rejects ID-less creation; deferred clients need durable persistence-before-send IDs, original intent/context retention and receipt-aware outcomes. Until implemented, current creation/import remains non-idempotent; this plan does not contain or fix that runtime gap.

Rollback must preserve durable receipt enforcement or disable affected creation; never restore an unrestricted non-idempotent retry path. Receipts must survive recovery and cannot be deleted to enable reuse. Downstream durable recovery, partial-import presentation, current storage/provider uncertainties and accepted-job policy remain distinct unresolved work. Do not invent automatic replay, exactly-once delivery, pricing acceptance or FX guarantees.
