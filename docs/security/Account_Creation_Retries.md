# Durable direct-account creation retries

Implemented configuration authoring, not approval of accounting or account use for posting. The existing FinanceLegalEntity lock remains shared with chart installation. Direct creation now requires a caller-persisted UUID operationId, normalizes the same allowlisted input for HTTP and alternate repository callers, and hashes sorted bounded JSON plus exact user/tenant/tenant-membership/selected-company-membership/company/legal-entity context. Currency, parent, description, defaults and trimmed strings are normalized; unknown authority fields and unsupported/non-JSON/excessive metadata reject. No financial amounts, mappings, FX or approval policy are introduced.

The entity lock serializes chart/account authoring; an additional transaction-scoped advisory lock serializes the operation UUID across entities. PostgreSQL primary/compound uniqueness, not the preliminary lookup or in-memory state, prevents duplicate acceptance. Current selected permission and stored company scope are reloaded after both waits, before inspecting any receipt. A matching receipt returns the original explicitly projected account creation result only after verifying its context/result binding and account existence. Original parent references are also reloaded within the current legal entity: the existing parent FK governs the current account link, not historical receipt JSON after that link changes. Conflicting content or context yields FINANCE_ACCOUNT_IDEMPOTENCY_CONFLICT (409) without business writes. Missing/revoked context fails closed. A receipt grants no access or posting authority, and its original creation result is not a claim about later configuration state; use current scoped reads for that state.

Account, immutable receipt, finance.account.created audit and accepted non-posting outbox fact commit or roll back together. New fully populated receipt ownership/member/account FKs are validated because this is a new empty table. Existing null ownership and NOT VALID historical constraints elsewhere remain uncertified. Result JSON is bound to its account/entity and never broadly serialized. Update/delete/truncate of receipts reject; existing accounts are not adopted into old/missing request identities. Preserve receipt/history on recovery and rollback; do not regenerate an ID after an ambiguous response. Existing account code uniqueness remains separate from intent identity.

API compatibility: POST /api/finance/accounts (mounted finance /accounts route) now requires operationId (UUID), supplied once per immutable intended creation and reused with the same selected context/content. Missing/invalid ID or unknown fields returns 400; matching authorized retry retains the existing 201 account response, with original id/timestamps and no new audit/outbox. code/name/type/parentId/allowPosting/isControlAccount/currency/description/status/entity/timestamps remain; metadataJson is no longer included in this explicit creation projection. Metadata may still be submitted and stored as non-authoritative configuration data. Bootstrap's existing immutable template/version identity is unchanged.

The actual local frontend lib/finance.ts createFinanceAccount helper does not send operationId, so that UI path now fails safely until the deferred client phase supplies durable context-bound immutable intent storage. No client edits or browser/device compatibility claim. No direct account creation consumer was found in the inspected driver source. Supported API callers with a stable ID can create and safely retry; this does not restore new invoice issuance, manual/automatic posting or financial approvals.

Migration 20261003160000_account_creation_receipt is additive. Apply before the new backend; stop old account writers during rollout because they can create accounts without retry receipts. Retain previous stop-old-finance-publisher and checkout/callback rollout requirements. Recovery/rollback must preserve receipts and authoring serialization or disable affected creation; never infer legacy receipt authority or loosen financial containment. Lock/statement/acquisition/transaction limits retain the existing two/five/two/ten-second bounds. Production pool capacity and changes after the final authorization read remain unverified/timing boundaries.
