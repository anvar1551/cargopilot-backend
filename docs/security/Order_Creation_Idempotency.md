# Durable order and import creation

Current enforced behavior, 2026-10-03: normal creation and import confirmation require a UUID `operationId` persisted by the caller for one immutable intent. Identity is `(tenantId, operationId)`; the same UUID in a different tenant is a distinct namespace, not access to another tenant's receipt. Within that namespace, user, selected company/membership/tenant membership, operation kind, versioned pre-quote fingerprint and complete ordered row sequence must agree. Conflicting reuse returns409 before business writes.

New98th additive migration creates immutable `OrderCreationIntent` and `OrderCreationReceipt`. Existing membership compound targets bind the actor/tenant/company graph; receipt compounds bind its accepted header and order owner. Non-null new fields do not backfill legacy records or establish complete tenant isolation. A normal header must acquire its ordinal0 receipt in the same commit; import headers can remain partially completed. Unique tenant-operation, header-ordinal and order targets plus PostgreSQL transaction advisory locks prevent competing creation. Append-only update/delete/truncate guards retain identity. Receipt ordinals must fall within the accepted count. Server defaults stamp acceptance; receipt insertion stamps confirmation.

Every lookup and write reloads the current exact tenant-bound membership, creation permission and explicit selected-company scope. Receipt return also repeats order tenant, owning company and creator predicates. Lost permission/scope, suspended context or an inaccessible order denies receipt access. These checks have statement-snapshot timing boundaries; they do not demonstrate instantaneous concurrent revocation.

Normal header, order, numbering, parcels, initial cash/tracking records, analytics outbox and receipt commit together. Import validates every raw row's authority and schema before acceptance, prepares only missing rows, then commits each row independently with its receipt and related records. Fresh context is checked again per row. Failed later rows preserve prior confirmations. Matching retries skip completed rows and continue missing rows. An immutable full-batch fingerprint rejects changes even to previously uncreated later rows.

The internal normalized-request provenance guard and prepared-row comparison prevent request objects or changed operational payloads from bypassing the repository boundary. This in-memory guard is not the deduplication mechanism; PostgreSQL uniqueness/locking and receipts are. The trusted pricing preparation can replace quoted service charge/currency; these server estimates are not approved financial pricing or FX acceptance. Original normalized request currency remains part of retry conflict comparison. Future uncreated import rows can use current eligible server quotes; no whole-batch price guarantee is invented.

## Retry / recovery boundary

Matching normal retries return the existing currently authorized order with201 and additive `creationReplay:true`, `downstreamRecoveryRequired:true`. New creation adds `creationReplay:false`. Stored receipts contain no addresses/phones or response snapshots; a retry returns current owned order state, not a historical response-body copy. Existing warning/payment keys are retained; replay warning isnull and payment checkout remains invoice-dependent.

Import201 retains `success`, `count`, `orders` and adds `replayedRows` and `downstreamRecoveryRequired`. Preview/template remain read-only; confirmation needs root operationId, separate from nested payment keys or CSV fields. No server-generated fallback exists. Confirmed replays do not run pricing seed, auto-booking, labels or full-replay HTTP invalidation. Partial import invalidation applies only when this request created a missing row.

Order confirmation is durable, not proof that post-commit work completed. A crash before/within pricing, queue, storage or provider work may require reconciliation; retries never repeat an uncertain completed-row effect or replace its identity. Existing best-effort pricing and authorized queue fallback remain for first execution. No new recovery/replay API or exactly-once external delivery is claimed. Legacy requests without IDs cannot be deduplicated retrospectively. Existing customer/address master containment, financial input restrictions, invoice-before-checkout, provider verification and financial execution blocks remain.

Receipted orders cannot be hard-deleted: the service returns409 before child reads/writes/storage cleanup, with the immutable receipt/order FK as the database guard. No automatic receipt deletion, order-number reset or cancellation redesign exists. Legacy deletion limitations remain separate work. Rollback must retain enforcement or disable affected creation; do not restore an unrestricted non-idempotent creation path.

Bounds: CSV1MiB/100rows, intent1MiB, individual intent text2048bytes, arrays100, depth12. Hashing uses explicit normalized fields, stable key ordering, ordered parcels/rows, normalized schedule dates and lowercase UUIDs. Confirmation prepares rows sequentially. Transactions admit within2s, lock timeout2s, statement timeout3s and transaction deadline8s. No provider/storage work occurs inside creation transactions. SLA lookup remains an existing separate read and is not redesigned here.

## Compatibility and remaining gates

Frontend/driver changes are deferred. They must persist operationId+original intent+exact selected context before send; retain IDs across timeouts/restarts; reject context switching; consume replay/reconciliation fields. Current ID-less creation/confirmation is incompatible. Preview and CSV formats remain usable. No automatic client replay or selection changes were made.

Uncertain downstream reconciliation and broader import presentation remain unavailable. Approved exact pricing/FX/accounting/checker eligibility, accepted-job version/cancellation/reacceptance/provider recovery, nullable/NOT VALID historical certification, provisioning, RLS, refresh families/distributed revocation, remaining dispatch/analytics/workers, Redis lifecycle and real storage/native transport/infrastructure remain open. This checkpoint restores bounded durable creation retries and missing-row recovery, not production readiness or full tenant isolation.
