## Current enforcement and API

POST /api/orders accepts optional root customerEntityId and addresses.senderAddressId / addresses.receiverAddressId. CSV preview/confirmation accepts optional columns with those three names. The existing import-level customerEntityId may select the customer; if a row also supplies a different customer, the request rejects. All populated IDs must be UUIDs and normalize to lowercase. Address IDs require an explicit accessible customer and must belong to it. Unsupported aliases, misplaced populated DTO reference fields and address-book mutations remain rejected.

Existing pickup/dropoff text and snapshot workflows remain valid without master records or customers.read. Referenced workflows additionally require fresh customers.read and the established customer/object scope through the selected authenticated company membership. Tenant-owned customers have no company-owner field: this slice does not invent one. The existing selected-company scope policy determines access; same tenant alone is insufficient. Order tenant/owner still derive from fresh shipment.create authority with explicit company scope. Financial fields, arbitrary pricing selection and ownership input remain denied; existing quote/FX and invoice-before-checkout containment is unchanged.

Preparation validates before quote work. The actual repository transaction revalidates before intent/order/number/business writes and retains referenced customer/address rows with FOR SHARE. Matching receipts require fresh creation authority and current master access before returning protected results; receipts never grant access. UUID-normalized reference content is included in the existing durable request identity. Changed references conflict; matching concurrent requests retain one order/receipt and downstream invocation. No migration or identity version change: reference fields already existed in the normalized intent, and populated references could not previously pass containment. Unreferenced successful intents retain their representation.

Linked creation responses use explicit customer/address projections, excluding passport fields. No automatic address snapshot hydration or address-book writes. Clients remain deferred; clients wishing to link masters must send the documented fields and retain their operationId/content across retries. Rollback must retain scoped reference validation or restore the specific reference containment, not unscoped linking.
