# Finance source-event and exception reads

Current enforced behavior: existing GET `/source-events` and `/exceptions`, service and repository lists require fresh selected tenant/company membership, `finance.exceptions.read` and an explicit stored company scope. No optional company-only entry point remains. Active tenant/company/legal-entity ownership is repeated at queries; missing/null/inactive ownership returns no rows. Status and bounded page inputs are allowlisted; cursors must match the same ownership and status predicates before keyset pagination.

Linked rules, documents and journals must belong to the selected legal entity. Rule lines require populated same-entity account bridges. Foreign/conflicting ownership is hidden; same-entity journal/document pairing conflicts and incomplete posted results reject the whole page, including its pagination sentinel. Reads never create legal entities, retry events or mutate configuration. Current eligibility is checked before reads; concurrent revocation after that check remains a timing boundary, not immediate distributed revocation.

Explicit response projections retain source/correlation identifiers, selected company/entity identifiers, status, attempts, authoritative dates and minimal rule/document/journal summaries. Raw payload, payload hash, worker claim details, scheduling internals and raw errors are omitted. The `{items,pageInfo}` envelope and event names remain unchanged. Unknown ownership/filter fields now reject400 instead of being silently stripped. Repository/service callers must supply verified actor context. Clients are deferred; consumers relying on omitted fields need later adaptation. No new detail endpoint or worker authorization bypass was added.

This is read containment, not source-specific financial acceptance. The original read checkpoint demonstrated that simple source-event reference FKs permitted cross-company/entity combinations. The later compound expansion below protects new/changed references; historical certification remains unresolved. No historical rows are mapped, no source execution is restored and no immutable rule acceptance, approved accounting mapping, checker eligibility or FX policy is inferred. Independent durable acceptance remains required for new financial execution; retry stays contained. Future additive source-reference constraints must protect new/changed references without claiming historical certification.

Validation/evidence and owned disposable cleanup are recorded in Security_Hardening_Backlog.md. Mocked HTTP tests are separate from real PostgreSQL predicates; no real provider, Redis, storage or client verification. Nullable/NOT VALID certification, broader financial dimensions, SQL immutability, distributed revocation, recovery and RLS remain release gates. Migration76 precedes this application slice; rollback must preserve authorization and output containment or disable the endpoints.

## Compound result integrity expansion (2026-10-02)

Current enforced database behavior: populated source legal entity must match its company; resolved rule, document and journal must match that legal entity. When both journal and document are present, their compound target must identify the same journal/document/entity tuple. A NOT VALID check prevents null legal entity with any populated rule/result reference. Five RESTRICT NOT VALID compound foreign keys and one journal result unique target are additive; old simple FKs remain intentionally retained even though Prisma now models the stronger relations. No old migration or historical financial row is edited.

Transitional combinations: a null legal entity with all three rule/document/journal references null remains permitted irrespective of status, and covered reads hide it. Pending/quarantined ingestion is the intended transitional use; SQL alone does not enforce that lifecycle. Null optional rule/document/journal references skip their corresponding equality checks. Document-only, journal-only or absent results with a populated entity remain possible in SQL, including an incomplete posted status. They are not accepted posting evidence; the existing read lifecycle/pairing checks and execution containment remain necessary. Existing mismatched historical rows are not certified by NOT VALID constraints, and unrelated updates may not recheck unchanged foreign-key columns. Nullable underlying tenant ownership remains transitional. Company/entity equality is not independently accepted accounting authority or legal classification.

All actual source writers were traced: generic ingestion/processing remains acceptance-contained, accepted custody ingestion reloads durable ownership, document/provider mutation producers remain contained. The new constraints guard persistence boundaries; no generic source execution, retry, approval or producer capability is enabled. No normal HTTP contract or client changes beyond the already scoped reads. Rollback retains scoped read and financial acceptance guards; it must not restore global access/execution. Schema/migration review covers target order, fields and restrictive actions plus retained simple constraints, not full semantic equivalence. Exact tests, failed attempts and owned cleanup are recorded in the backlog.
