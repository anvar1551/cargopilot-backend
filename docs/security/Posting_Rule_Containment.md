# Posting-rule ownership and configuration containment

Current enforced behavior: list/detail and service/repository entry points require fresh selected tenant/company context, `finance.postingRules.read` and an explicit stored company scope. Active tenant/company/legal-entity ownership is repeated at the actual queries. Rule lines and account parents must belong to that legal entity. Missing/null/inactive ownership produces no records; foreign details and cursors return404. Keyset pagination verifies cursor ownership instead of applying a global Prisma cursor.

Explicit bounded projections retain rule and line identifiers, lifecycle/version/source fields and safe account display data. Arbitrary `conditionsJson` and `dimensionsJson` are omitted; these untyped objects cannot prove referenced ownership or safe disclosure. More than50 lines rejects instead of truncating configuration. This is a backend contract change requiring later client review; no frontend/driver implementation or compatibility claim is made.

Configuration create/version/status now requires fresh `finance.postingRules.manage`, explicit company scope and matching authenticated actor/company, then denies409 `FINANCE_POSTING_RULE_APPROVAL_REQUIRED` before transaction/audit/outbox/business writes. Existing create defaults to active, versioning deactivates other rules and status enables execution; no immutable independent checker acceptance exists. Caller approval fields, overlapping roles or persisted active status are not approval. The original calculations/workflow bodies remain behind containment.

No migration or historical rewrite in this slice. Current simple posting-rule-line/account foreign keys permit cross-legal-entity references; actual disposable PostgreSQL probes demonstrate this gap. Runtime reads hide the entire inconsistent rule, not merely its foreign account. A later additive compound ownership bridge/constraint slice must protect new/changed references without inventing historical ownership, with certification limits explicit.

Authoritative cash custody/outbox/source validation remains separate from approval of accounting configuration. Worker source inspection confirmed active rule selection could drive new automatic postings without durable configuration acceptance. The follow-on described in Automatic_Finance_Execution_Containment.md now denies unsupported new execution; this does not establish approved mappings or complete finance containment. Synthetic cash tests prove mechanics and source provenance, not approval of accounting policy.

Required business decision: company-scoped independent checker eligibility and immutable accepted rule-version identity, permitted configuration activation/deactivation/version/supersession and cancellation/revocation behavior for already accepted source events. Separate actors are already required by architecture12; no thresholds, accounting mappings, FX rules or override are invented. Until a verifiable acceptance contract exists, unsupported new execution must remain contained. Posted records must not be rewritten to repair missing acceptance.

Validation commands/results and disposable cleanup are in the backlog. Mocked HTTP authorization is distinct from real PostgreSQL predicates/probes. No existing-service, client, dependency, dist, push or deployment changes. Nullable ownership/NOT VALID historical certification, financial dimensions/source acceptance, SQL immutability, provider/storage recovery, distributed revocation/Redis and RLS remain release gates.
