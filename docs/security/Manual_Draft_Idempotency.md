# Manual journal draft identity

Current enforcement: fresh selected tenant/company membership, `finance.journals.create`, explicit stored company scope and active owned legal entity precede every creation or retry. Receipt possession never authorizes access. Manual posting/reversal remain denied with `FINANCE_MANUAL_APPROVAL_REQUIRED`; drafts and client source markers are not accounting acceptance.

Dedicated nullable FinanceDocument fields bind new manual drafts to the authenticated user, tenant, tenant membership and company membership, selected company and normalized immutable request fingerprint. Decimal formatting, JSON key order and UUID case are normalized; line order, exact requested values (including values that round to the same advisory draft), dates, metadata, dimensions, source markers and legal-entity/base-currency context remain part of intent. JSON depth/node/byte, line count and decimal representation are bounded. Existing draft calculations are retained, not certified as approved pricing/FX policy.

PostgreSQL transaction advisory locking serializes an entity/key across all callers. The existing entity/key unique constraint remains the durable backstop. Matching retries validate the authoritative journal/document/line graph and normalized stored snapshot, returning the original projected draft without number allocation, audit or outbox duplication. Different content/context, changed stored state, legacy unbound keys and incomplete results reject with 409 `FINANCE_DRAFT_IDEMPOTENCY_CONFLICT`. No in-memory or read-then-create concurrency claim is used.

Migration `20261001200000_manual_draft_intent` adds five columns, a legal-entity compound unique target, four compound foreign keys and an all-or-none receipt check. The relationships bind entity tenant/company, membership user/tenant/company and the exact company/tenant membership bridge. They establish ownership equality, not legal classification or approval eligibility. Constraints are NOT VALID: new/changed references are protected, historical rows are not certified. All-null legacy receipt fields intentionally remain possible and confer no retry authority. There is no default tenant or historical backfill.

An update trigger rejects rebinding an unbound historical document, changing/clearing an existing binding or changing its key, number, creator or financial/document basis. It does not implement general journal-line immutability, approvals, cancellation, retention or privileged direct-SQL defense. Retry comparison detects changed journal headers/lines; it does not repair them. Posted-record protections and controlled reversal rules must remain intact when acceptance is later designed.

Backend API impact: create/reverse bodies and draft lines now reject unknown fields rather than stripping caller ownership/approval fields. Create responses retain the inspected journal/document/line projection and exact decimal serialization, excluding receipt context/hash, actor and raw metadata. Existing idempotency keys without a bound receipt cannot be adopted. Clients must retain an immutable intent/key within the original context; no client implementation or browser/device compatibility is claimed in this backend phase.

Rollout requires the additive migration, matching generated Prisma client and source. Older writers can still produce unbound drafts, which cannot be retried as accepted receipts by the new implementation. Do not roll back to permissive duplicate handling or unapproved posting. Existing database execution/backfill is not authorized.

Validation is recorded in the backlog. Prisma WASM syntax validation, manual relation/SQL review and selected PostgreSQL catalog assertions are distinct; none is complete semantic schema-to-SQL equivalence or historical certification. Database tests exercise real locking, uniqueness and transactions with synthetic fixtures; storage/provider/Redis/transport are not exercised.

Blocked approval decision: company-scoped independent checker eligibility, immutable proposal/version acceptance and posting/reversal/cancellation/revocation lifecycle. Separate maker/checker actors are already required, without invented thresholds or overrides. Approved pricing/FX provenance and accounting mappings remain separate blockers. Next ready backend slice is scoped trial-balance reads, with no configuration creation or mutation; broader source execution/dimensions and RLS remain deferred.
