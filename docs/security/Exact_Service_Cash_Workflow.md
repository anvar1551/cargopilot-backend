## Enforced contracts

- `POST /orders/:id/service-payment-instruction` uses current accepted `billing-operator.v1` / `billing.payers.bind`, selected company/entity and existing order/customer scopes. Strict body: `operationId` UUID, `billToId`, literal `method: CASH`, `collectionParty: SENDER | RECIPIENT`, bounded `evidence` (1–500) and `reason` (1–1000). Server derives ownership and actor. Response is `{id,orderId,method,collectionParty}` in the existing billing envelope. No monetary/ownership fields, implied instruction, online-to-cash conversion or payer adoption. Binding is before price acceptance; one immutable instruction/order. Fresh authorization precedes matching retries; different normalized content/context conflicts.
- Existing standard price acceptance or independent exception/revision approval creates `OrderServiceCashObligation` in the same transaction as approved price, current pointer, expected compatibility history/mirrors and audit. Its durable ID is the approved snapshot ID. Compound references bind tenant/company/entity/order, bill-to/payer, approved amount/currency/policy and instruction. Exact Decimal(20,4) basis is authoritative; Float mirrors can reject inconsistency but never determine money. Mirrors that cannot round-trip reject instead of rounding authority.
- Normal order/import creation no longer creates collectible cash rows from quote/COD Float inputs. Existing free-text creation and request/row idempotency remain; each imported order needs its own explicit billing acceptance. Import remains independent per-row partial success, not whole-batch atomicity or downstream completion.
- Zero accepted service price is recorded but not collectible. Initial zero creates no CashCollection; an untouched positive-to-zero revision preserves existing expected history/mirror at zero. Negative totals remain rejected; an approved 100% discount still needs an independent exception approver. Zero-value invoice issuance explicitly remains unavailable under the existing positive-invoice contract.
- Cash collection now requires `obligationId` (the current approved snapshot UUID) with the existing stable operation ID. Cash queue/preflight and mutation results add `obligationId`; reads also add `collectionParty`, and expose exact decimal-string amount/currency before collection. Persist the original ID/content across uncertain responses; do not replace it with a new ID or newly discovered approval. Foreign, obsolete, unproved and zero sources reject. No new driver/company/warehouse grants.
- SENDER collection is limited to assigned/pickup_in_progress by the eligible assigned local driver. RECIPIENT collection is limited to at_warehouse by the exact scoped warehouse actor, or out_for_delivery by the accepted last-mile local driver. Fresh capability plus authoritative assignment/custody still required. SENDER picked_up and RECIPIENT delivered recheck exact positive collection evidence under the parent lock. Missing/stale accepted basis blocks the applicable transition once an instruction is bound. Creation defaults alone never establish approved obligations; legacy guards remain conservative.
- Before collection, an independently approved revision can supersede only untouched authority. The original instruction/bill-to remain immutable; supersession appends versions and expected events. Any cash activity/holding, invoice, paid/partial marker or PaymentIntent freezes revision (including pending reservations, failed/uncertain attempts, not only successful payments). This is intentionally conservative; no payment allocation/reset/reconciliation policy is inferred. Old approval receipts are historical results, never republished current pointers or new collection/invoice authority.
- Order locks serialize price approval, collection, transition and invoice; identity/reference pins and accepted-grant locks precede domain locks. Protected instruction/obligation UPDATE, DELETE and TRUNCATE rejection, a database current-price fence and compound source FKs defend new writes. Application freshness remains mandatory. `RestrictedCashState_service_basis_fk` is NOT VALID: new/changed references checked, historical holdings not certified or adopted. Owners/schema administrators remain outside application tamper protection.
- Parcel intake/reassignment does not move cash. Existing offer/acceptance retains origin custody until exact recipient acceptance. Separate authorized warehouse checker settlement preserves source amount/currency and human separation. It neither marks invoices paid nor creates executable accounting facts. Manual invoice requires current exact approved service basis and eligible independently configured same-base-currency policy; invoice outbox remains held.

## Rollout and remaining blockers

1. Apply the additive migration before new billing/cash writers; stop old order/import/cash/price publishers. No migration was applied to an existing database. No backfill/adoption; legacy unlinked expected rows reject initialization and legacy unproved holdings remain inaccessible.
2. Deferred clients must explicitly bind CASH timing before accepting price and persist current obligationId with immutable cash intents. Price changes require new independently approved authority; stale collections are rejected, never silently migrated. Existing offered/accepted transfer and checker contracts remain unchanged. No client implementation or native-device claim.
3. Merchant COD still rejects `CASH_MERCHANT_BASIS_UNAVAILABLE`: verified merchant/source/beneficiary, exact goods amount, accepting authority, amendment/cancellation and timing remain unapproved. It is separate merchant money, not service revenue.
4. Accounting mappings/approved posting, payment allocation/refunds/corrections, FX, suspended cash-holder recovery, linehaul/warehouse-to-warehouse cash transfers and zero-value invoices remain unavailable. Service-charge settlement is custody evidence, not financial reconciliation.
5. Real owner keys/private credential delivery/reviewed company configuration, infrastructure, historical/null certification, RLS, source-to-dist provenance and client/device verification remain release gates. Service-charge backend readiness is not production readiness.
