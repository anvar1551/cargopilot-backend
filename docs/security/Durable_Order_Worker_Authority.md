# Durable label and carrier operation authority

Checkpoint: `3ed8fbe7e9698c2e798a5d31f91595c1148d0663` commits the reviewed direct child-access containment. This worker implementation remains uncommitted for review and supersedes that checkpoint's temporary worker blocks only as described here.

## Current enforced behavior in this source

Human job creation still uses fresh selected-membership authorization and the established parent order permission/object-scope checks. Acceptance stores a narrow durable operation grant, not a human session or an unrestricted system role. Execution reloads PostgreSQL records by ID; queue ownership/payload fields and current human login state confer no authority.

New `OrderLabelJob` rows store tenant, owning company, acceptance time and the fixed `label.generate` capability. The compound foreign key targets the order's tenant/id/owner company. The SQL check permits either a wholly absent legacy grant or a complete supported grant; partial grants are rejected. Workers exclude unaccepted legacy jobs, reload the claimed row and verify worker/attempt fencing, active tenant, active owning company of type company, matching ownership and every parcel's parent before rendering or uploading. Labels use tenant/company/order/parcel object keys and parcel-ID local filenames. Already-labelled parcels are skipped; completion/failure bookkeeping is conditional on the current lease and attempt. Authorization failures do not create support tickets.

New carrier outboxes store accepted tenant/order ownership; existing companyId is the owning company. Compound ownership and complete-grant checks apply. Booking/track/cancel acceptance rejects providers for a different owning company, including other companies in the same tenant. Existing organization/object restrictions remain. Accepted idempotency rows are not rewritten or reset; matching create/cancel requests return existing work, while unaccepted/conflicting rows fail. Leg row locks serialize these creation paths; this specific acceptance locking has source and mocked evidence, not an executed concurrent HTTP booking test.

Carrier dispatch reloads the accepted operation, order, active tenant/company/provider, provider code/environment, child leg and stored command metadata before loading provider secrets or contacting a provider. Only create_shipment, track and cancel_shipment are supported capabilities. No worker impersonates the maker or chooses a membership. A conditional executionStartedAt admission allows one mutating provider invocation. A previous admission, existing attempt history, unsuccessful admitted mutation or denied authority holds the operation for recovery instead of replaying it. A held result produces a bounded sanitized diagnostic, no outbox attempt/failure event, and no provider call. Conservative holding can also occur after admission but before the network request. Automatic safe retry classification for these held mutations is unresolved; existing configured retry ceilings/backoff and unrelated-domain retry policy are retained, without claiming that mutating carrier replay is safe.

Canonical outbound-response application reloads and locks the canonical row, accepted outbox, parent ownership and child leg. Event/company/provider/aggregate/operation must agree. The latest matching durable delivery attempt supplies the response and occurrence time; queued/canonical response payloads cannot replace that result. The leg/tracking changes and processed receipt commit together. A processed duplicate has no business effects. Short PostgreSQL locks protect parent tenant/company ownership during application, with no provider network call inside that transaction. Failure bookkeeping cannot overwrite a processed receipt and is fenced by processAttempts. Existing status mapping, financial inputs and tracking payload contracts are retained.

## Contained workflows and recovery policy

- Legacy label jobs and carrier outboxes remain unaccepted; no historical attribution or automatic reacceptance occurs. Human-authorized inline/fallback label generation remains available.
- Inbound carrier webhooks retain raw-body verification and ingestion semantics but remain blocked from order application: a verified provider payload alone does not establish an unambiguous accepted operation/leg association. No payload-ID or first-matching tracking-reference fallback remains.
- Accepted operations survive maker logout, refresh expiry and maker membership/permission revocation. Tenant/company/provider suspension denies execution; label denial uses the existing bounded retries and may exhaust, while carrier denial holds processing for explicit review. This is operational suspension, not an immediate cancellation guarantee.
- No new cancellation/recovery API or grant-clearing procedure is introduced. The necessary business decision is which authorized operation/actor may cancel or reaccept accepted jobs, and how to reconcile a carrier request whose provider outcome is uncertain. Until that protocol is approved and tested, held mutations must not be replayed by clearing executionStartedAt. User revocation must not silently transfer work to another identity or company.
- Existing pending/failed label claim rules, maxAttempts, delay policy and membership-bound stale fallback remain. There is no new autonomous stale-label lease recovery. Outbox/canonical stale-claim timing remains. Holding a carrier row leaves it eligible for periodic stale consideration, but the durable admission prevents another mutating provider invocation.

## Compatibility, migration and limitations

Apply the new additive migration before running this source; generate the application client from reviewed schema during the normal build. No migration was applied outside the disposable instance. Clients and event names/response shapes are unchanged; new label keys are scoped, and existing downloads retain their reviewed compatibility behavior. Queue-only label completion resumes for newly accepted jobs. Carrier creation/cancel can perform one accepted dispatch and apply a persisted result; tracking results can be applied. Legacy events, inbound webhooks and uncertain mutation recovery remain contained.

All-null grants still bypass the additive compound checks and are hidden/denied by executors. Database constraints establish ownership equality, not legal classification, workflow authority or immutable grants against privileged database access. Active status and purpose checks remain application enforcement. Tenant-null records, broader repository scoping, RLS, cash, dispatch redesign, import recovery, client offline identity binding, finance authority/concurrency and previously recorded release blockers remain open.

External effects have a timing boundary: suspension or lease changes after the last read can race with rendering/storage/provider work. No atomic revocation across PostgreSQL and external systems is claimed. Label fallback/worker overlap and uncertain storage writes may overwrite the same deterministic object or leave an object without its database attachment; external cleanup and broad lease recovery remain unverified. Outbox result persistence and canonical enqueue are still separate transactions: a crash after provider success may require reconciliation and event repair. Provider idempotency support, real network/storage transport and infrastructure controls are not verified. Rollback must retain containment/grants or disable affected operations; it must not restore unscoped worker access.
