# Administrative delegation containment

Historical evidence below: the broad manual ERP/support bootstrap described
here is now disabled by Tenant_Onboarding_Foundation.md. Controlled signed-permit
provisioning grants only the approved six-key profile; invitations/delegation and
role-management mutations remain contained. No generic administrator bypass.

## Plan / current enforced behavior

Baseline 3d7f4915382c391d3eb52b371a388dcfe8effa3b. Inspect public identity routes, service exports, role/permission/scope writers, provisioning scripts and actual frontend consumers. Contain unapproved grant paths before any business reads or effects; retain fresh scoped management reads and existing login/refresh/password contracts. No schema/migration, client rewrite, existing-data cleanup or invented delegation policy.

Confirmed source defects: admin PATCH could replace arbitrary roles, convert empty scopes to company scope, link user-global customer identity and change a shared human's email; company role resolution admitted null-company platform roles. Role creation bound any stored permission/isOwnerRole without a ceiling or transaction. DELETE could permanently delete a global identity or revoke every tenant's refresh sessions. Permission seeding automatically added every new permission to all system owner roles. These were source findings, not executions against an existing database.

HTTP POST /api/auth/roles, PATCH /api/auth/:id and DELETE /api/auth/:id now return 403 / DELEGATION_POLICY_REQUIRED before parsing, credential lookup or business effects. This deliberately contains both grants and the unsafe global deletion/revocation contract. The same service exports reject before lookup/hash/mutation, including administrative enrollment already blocked at HTTP. Login, refresh, self password change, logout and existing company/object policy are retained. Possession of membership.invite, role.bindPermissions or policy.override creates no delegation authority and no self-approval exception.

Management permission catalog, company role catalog and user directory require the exact active selected identity/company-membership/tenant-membership/company/tenant tuple, freshly reloaded, the existing read/action permission and explicit selected-company scope. Missing/foreign/null/revoked context fails closed. Catalog roles exclude global/system roles even with includeSystem=true. Directory lists and counts require populated active tenant bridges in the selected company; role projections exclude foreign/system definitions. Shared User.warehouseId/customerEntityId are no longer selected or displayed as management assignment authority; compatible fields return null. Remaining scalar branch/scopes are membership metadata, not validated delegation grants or a certificate of historical typed-reference correctness.

Permission seeding now maintains the server-controlled permission catalog only; it cannot automatically expand existing roles. It was exercised using mocked Prisma only. No seed/bootstrap command was run. The manual bootstrap-erp-access script still provisions roles/scopes with broad synthetic installation authority; it is outside normal HTTP and is NOT an approved production/delegation workflow. Any execution needs separate scoped provisioning review, ceilings, typed resource validation and protected audit.

## Compatibility / decisions / deferred enforcement

The inspected frontend lib/iam.ts, lib/users.ts and manager/users page call these management APIs and display returned backend error messages. Viewing remains subject to explicit company scope. Create-role, edit-access/profile, delete-user and already-contained create-user buttons cannot succeed; backend explains the policy block. Clients were not weakened or modified. Driver auth consumer does not call these management APIs. No browser/device claim.

Business decision needed to restore grants: designate explicit tenant/company delegators; define grantable permissions/roles (including forbidden platform/override/maker-checker combinations), typed resource ceilings, actor separation and approval records, revocation authority, identity/profile versus membership ownership, and deliberate initial provisioning. Mere role names or possession of a requested permission are insufficient. A future approved mutation must lock/revalidate actor and target context, update only allowed records, and commit immutable privileged audit plus a durable authorization-version increment atomically. No such version column exists in the inspected current identity schema; existing invalidation is process-local cache clearing. This slice performs no accepted privileged mutation, so it does not claim audited delegation, grant ceilings or versioned/distributed revocation implemented. Existing dangerous grants are not removed from data and still require reconciliation/reprovisioning review.

Rollback must retain denial or disable these endpoints; restoring arbitrary legacy grants/global deletion is unsafe. Typed reference certification, invitation-only provisioning, company-membership assignment, broader policy.override, maker-checker, finance, refresh families and all previous release gates remain open. No production-readiness/complete isolation claim. There is no new PostgreSQL transactional behavior; no disposable database run was needed for unconditional no-write denial/read predicates. Unit predicates are not database/concurrency evidence.
