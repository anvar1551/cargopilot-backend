# Selected self-service driver telemetry and presence

Current enforced behavior (2026-10-03): the five driver location/telemetry/presence/heartbeat entrypoints retain complete AppUser context. Every operation freshly reloads the exact active selected company/tenant membership through loadAccessSnapshot and requires drivers.telemetry. A drivers.manage claim or a driver's permission in another membership grants nothing. Self identity is the scope; delegated driverId is denied. Optional orderId additionally uses existing fresh shipment.view/order scopes and requires the selected owning company and assigned driver. Warehouse/global driverType/first membership never establish ownership. No global User profile/settings writes occur.

Bounded plan: preserve the five entrypoints, isolate self-service cache records, require original client intent context, revalidate membership and optional parent ownership, suppress manager delegation/global delivery, test guards and HTTP/store consumers. No new ownership schema or client code. Migration is application-only; existing unowned keys are never read or relabelled. Secure rollback must retain these guards or disable the five endpoints, never restore global keys/queries/publication.

Breaking client contract: bodies require context:{userId,tenantId,tenantMembershipId,companyId,companyMembershipId}. GET /presence requires the same JSON object encoded in query.context; optional driverId must equal authenticated self. The context is an original-intent comparison, not authorization authority. Missing/foreign/unbound context and unsupported fields fail closed. Legacy offline presence requests remain blocked; clients are deferred. No consumer/browser/device compatibility claimed. GET uses no-store. Current routes retain their paths and response envelope, but initial enabled:false and updatedAt:null represent no selected-context opt-in. Location requires explicit selected-context opt-in. Membership-scoped sharing expires after24hours rather than inheriting global User.liveLocationEnabled. recordedAt in the response is server receipt time; optional client recordedAt is separately returned/stored as clientCapturedAt and never drives online status.

Selected cache partition v1 includes tenant/company/company-membership/tenant-membership/user, encoded into a SHA256 key. Presence preference and latest telemetry are separate atomic SET/EX records. No legacy keys, local/stale fallback, global GEO index, stream or replay. Presence reads expose only server heartbeat metadata, never cached location or order IDs. No new driver location broadcast; broadcasted:false and existing SSE containment stay explicit. Full manager map, delegation and scoped realtime ownership remain unavailable. Cache records are ephemeral and are not durable business receipts or offline queue confirmation.

Failure/recovery boundary: unavailable/not-ready/write-failing storage returns a failure, not accepted telemetry. Existing shared Redis client deadlines/retries are reused; no Redis connection was opened. A timed-out command may still execute, and an HTTP timeout does not prove commands/connections stopped. Redis lifecycle/backpressure remains a release gate. A SET has an uncertain outcome after timeout; do not claim durable retry/restart safety. Same-context concurrent cache updates use Redis last-write semantics; opt-out can race with already-authorized coordinate writes, and authorization can change between the PostgreSQL snapshot and Redis effect. No immediate revocation/atomic cross-service guarantee. The new reader never exposes cached coordinates; restoring protected delivery needs fresh recipient checks and explicit opt-out/revocation policy. These limits are not financial transaction guarantees.
