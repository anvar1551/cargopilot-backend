# Selected payment configuration containment

Current enforced behavior: company payment policy, provider configuration inventory, available checkout providers and local configuration checks resolve the exact active selected CompanyMembership/TenantMembership/tenant/company tuple. Stored action permissions and an explicit company scope are mandatory; warehouse/customer scopes and the same user's other memberships are not configuration authority. Requested company is only an equality assertion. Final business queries repeat selected company, tenant, active company type and active tenant predicates. Missing IDs/context/bridges/scopes fail closed. Reads do not create defaults; absent policy is disabled.

Public configuration DTOs omit credential values, including serviceId (the Stripe webhook signing secret), encrypted/masked secrets, merchant/account values and surplus fields. Availability and local checks expose only configured-field booleans. Local checks decrypt only after a selected scoped lookup; decryption exceptions and HTTP configuration errors are sanitized. `validationMode: local-configuration-only` explicitly excludes provider transport or account verification. Config inventory is bounded to eight enum combinations; supported Stripe availability to two environments. Disabled/foreign/unowned configurations cannot become checkout availability, and a policy locking an unsupported provider returns none.

Contained, not restored: policy PUT and provider POST/PATCH reject409 PAYMENT_CONFIGURATION_APPROVAL_REQUIRED after fresh manage permission/company scope (PATCH additionally resolves an owned record with an id-only projection). No credential encryption/decryption, write, transaction, audit/outbox, file or external operation occurs for those denials. The approved architecture section12 requires actor separation for sensitive financial configuration, but no independent durable configuration version acceptance or eligible checker policy exists here. Needed decision: who may independently approve payment enablement, provider credentials/environment/account changes, and how accepted versions/cancellation are retained. This slice does not invent eligibility or bypass that requirement. Existing stored configuration may still support the narrowly covered Stripe workflow; historical independent acceptance is not certified. No application process or live credentials were accessed.

The unused context-free isCompanyOnlinePaymentsAllowed export is removed (no source callers found). Existing Fastify routes and signatures remain, with selected-company rather than all-user-company inventory, credential field removal, fixed error messages and explicit write containment. Client implementation remains deferred; settings screens expecting credential echo or direct mutation need a later approved flow. Other providers remain listed as configuration inventory only, not offered for checkout. Single selected company scope does not grant all company orders; existing order/object checks are unchanged.

Authorization is fresh at entry and active ownership is repeated at the final read. This is not a lock-based immediate revocation guarantee: a change after membership verification may overlap an in-flight read. No mutation is restored and no PostgreSQL concurrency claim is made. No schema/migration changes; historical/null certification, immutable invoice/entity/configuration acceptance, cash allocation, pricing/FX/accounting, provider recovery and remaining integration/worker/RLS/infrastructure release gates remain open.
