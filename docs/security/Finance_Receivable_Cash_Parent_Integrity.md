# Receivable allocation and cash application parent integrity

Current enforced behavior: migration81 adds nullable legalEntityId bridges to FinanceReceivableAllocation and FinanceUnappliedCashApplication, compound id/entity targets on their two parents, three RESTRICT compound foreign keys, two entity-leading child indexes and two NOT VALID bridge-required checks. Existing simple parent foreign keys remain deliberately retained. Populated allocation/entity must equal its receivable; cash application/entity must equal its cash parent and optional receivable. This protects same-tenant different-company/legal-entity references as well as different tenants through the existing authoritative entity/company/tenant chain. It does not prove that every parent operational/source relationship is correct.

No backfill, inferred ownership, existing financial edits or constraint certification. Schema fields stay nullable to represent historical records. New inserts and updated rows cannot leave a bridge null because PostgreSQL checks the NOT VALID required-bridge constraint; relevant new/changed references must satisfy the compound foreign keys. Existing untouched null or conflicting rows have not been certified. A refund application may intentionally omit receivableId, skipping only that optional relationship; its cash/entity relationship remains mandatory for new/changed rows. Other source, payment/refund, order, customer, currency and amount relationships remain independently checked by scoped reads and are not yet all compound database constraints.

All five private projector child-create paths derive legalEntityId from the server-resolved entity, not event metadata. Covered invoice/payment/refund projection additionally reloads active bound entity/company/tenant and the stored source event identity before its lock or business writes. This is ownership/correlation verification, not independent accounting-source acceptance. The only production caller remains the transaction in prisma-finance.repository.ts, behind existing automatic-execution containment. Nothing restores invoice issuance, accounting rules, supplier/provider acceptance, approval or FX policy. Advisory locking, existing operation uniqueness, exact calculations and transaction boundaries remain intact; no generic worker bypass or human impersonation added.

Read containment is retained. Populated conflicting child entity bridges now fail the report; legacy null children must still prove the complete existing source/order/currency graph to be visible. The child legalEntityId is not exposed as a new response field. No client work or public mutation contract added. Old application versions that omit the bridge will fail new writes after the migration; deploy bridge-writing source together with the expansion. Rollback must preserve these protections or disable projection, never drop enforcement to resume unscoped writes. NOT VALID historical certification remains a later explicitly authorized task.

Evidence is recorded in Security_Hardening_Backlog.md. PostgreSQL duplicate projection proves one committed allocation for the tested schedule, with the competing raw projector transaction rejected by existing uniqueness; it is not a public receipt/retry contract or exactly-once external delivery. Mocked tests cannot prove database isolation. Source acceptance, parent operational graph constraints, monetary/source constraints, broader posting dimensions, nullable ownership, RLS and prior release gates remain open.
