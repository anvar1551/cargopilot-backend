# Canonical integration source integrity

Current enforced behavior: populated outbox/webhook provider references must agree on company, domain, provider code and environment. Canonical references must agree on company/provider/domain/code with the configured provider and exactly one persisted source. An inbound source is a webhook; an outbound source is an outbox. New canonical writes require non-null company/provider and the correct exclusive source ID. Compound equality proves relationships, not legal classification or independently approved accounting configuration.

Migration `20261003000000_integration_source_context` adds five unique targets, five compound foreign keys and two completeness checks. New foreign keys/checks are `NOT VALID`: they protect new/changed references but do not certify historical rows. Old simple foreign keys deliberately remain as additional existence checks, including the preceding canonical outbox FK. The selected Prisma relationships describe the new compound targets; the retained redundant physical constraints and SQL-only checks are intentional, not unexplained drift. Offline schema validation, selected source/SQL comparison and native query/constraint tests do not constitute complete semantic schema-to-SQL equivalence. No historical migration or record was edited.

Nullable expansion: an outbox without providerId still bypasses its compound provider check; existing worker authorization rejects unaccepted/unbound execution and metadata reads hide it. Raw webhook security records may have both companyId/providerId null, but not a partial pair on new/changed rows; they cannot supply canonical authority. New canonical records must be bound, but pre-existing invalid rows remain uncertified. Claim candidates exclude structurally unbound/dual-source records and inactive provider/company/tenant context, so the new completeness check cannot make such legacy rows abort the entire claim batch. Complete historical rows with conflicting tuples still require executor checks and later certification; no immediate revocation or universal database isolation claim is made.

Canonical enqueue now reloads the source inside a bounded transaction with a share lock. Inbound metadata derives from the persisted verified body digest and normalized event, whose company/domain/code must agree. Outbound metadata uses the existing narrow accepted carrier capability to reload order/provider/leg context and the committed terminal delivery attempt. Create, track, cancel and terminal-create-failure projections match the inspected publisher contract. Pending/retry/uncertain attempts do not become successful output. Input ownership, timestamp, event and payload fields are assertions against those records, not authority. A recorded attempt authorizes metadata persistence only; business application still uses the established carrier binding/transition executor. No human membership is impersonated; initiating login is not execution authority.

Existing durable source uniqueness governs duplicates. On P2002, a fresh source proof and an exactly matching receipt are required. The natural-key uniqueness fallback cannot return another source/company/provider's result. Conflicts reject409 without overwriting receipts or resetting accepted operations. Source normalization, IDs and payload are preserved; no immediate provider replay is added. Transactions contain database work only: maxWait2s/timeout5s, statement3s/lock1s. This is not complete global pool/backpressure or network-partition certification. Worker leases/retry limits and domain processing remain unchanged outside the structural claim filter.

Compatibility: valid inspected gateway/publisher sources retain their event/payload contracts. Unbound, conflicting, missing-normalization or nonterminal output enqueue is unavailable; unsupported provider business processing remains contained. New/changed reference mutation/deletion may now fail where older simple FKs allowed it. Historical pending invalid records are not silently assigned ownership, edited or deleted. Rollback must retain these constraints/source checks or disable affected execution; it must not restore unscoped writes. Clients are deferred.

Evidence: 28 new source guard unit cases (27 in the125-case affected milestone plus1 focused terminal-failure case), affected worker/binding/metadata tests,12 distinct actual PostgreSQL cases at88 migrations, offline validation/generation and final no-emit. The earlier9-case run and final12-case run overlap; do not add them as21 new cases. Native tests exercise actual canonical enqueue, concurrent duplicate sources, different-company identity collisions, forged context/content, populated relationship insert/update rejection, rollback and legacy claim containment, plus affected metadata reads. No provider/storage/Redis transport or exactly-once external delivery was executed/claimed. Exact owned-run cleanup and commands are in the backlog.

Remaining technical work: normalized webhook source relationship constraints and writer derivation, atomic ingress persistence/deduplication across raw/normalized/pending records, immutable non-financial configuration action/version auditing, secret pointer/version serialization and routing authority. Financial acceptance/checker/accounting/FX policies and provider recovery/cancellation remain unresolved. Historical/null certification, broad scoping, infrastructure and RLS release gates remain open. Containment is not restored functionality.
