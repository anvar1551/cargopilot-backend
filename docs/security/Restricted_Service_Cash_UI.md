# Restricted service-charge cash UI

Bounded plan: (1) reuse accepted supplemental capability, exact order obligation and transfer target checks for no-store named discovery; (2) add a separate cash workspace with strict immutable context-bound intents and contain obsolete cash submissions without deleting their records; (3) exercise actual restricted HTTP/PostgreSQL collection, offer, acceptance and independent settlement plus focused client persistence tests; (4) review and commit backend reads and frontend integration separately.

Supported contract: service_charge only; collect requires operationId and obligationId (accepted price identity), optional warehouseId; offer requires operationId, expectedEventId, recipientMembershipId and explicit nullable recipientWarehouseId; acceptance requires operationId, expectedEventId and offerId; settlement requires operationId and expectedEventId. All accept optional bounded note. Order identity is in the URL. Amount/currency are never submitted. Offer retains the existing holder; only recipient acceptance transfers custody. Settlement is warehouse-held, separate-human and does not pay an invoice or post accounting.

Discovery must use accepted capability, current selected membership and existing base resource restrictions. Named recipients are candidates validated by the same target function as offer execution; mutations always revalidate. No new grant, schema or cash mutation policy. Legacy unproved cash remains unavailable. Historical confirmed receipts are distinct from current preflight.

Focused validation completed as recorded below. Visual inspection is pending; no browser-channel bypass is authorized. Existing concurrency, rollback, revocation, socket and DOM-06 monetary evidence will be reused where unchanged. No S3, accounting, merchant COD or production readiness claim.

## Completed contracts and rollout

GET /api/orders/cash/access reloads the selected membership's accepted supplemental profile, acceptance ID, legal entity, exact permissions/kinds and named owned warehouse ceiling. It grants nothing. GET /api/orders/:id/cash/recipients accepts warehouseId (required for driver-to-warehouse), limit 1–25 (default 10) and opaque cursor. It requires cash.handoff, proven current cash ownership and current holder, then calls the same recipient target checks used by offer execution. Warehouse-to-driver requires accepted last-mile custody. Candidates are scanned in bounded pages (limit+1); a page can contain no eligible items and still have a next cursor. Cursor binds selected context, capability acceptance, order, custody event, destination and limit. No global users/driver selector or request-owned authority.

Queue limit 1–50/default 25 and the existing opaque cursor remain unchanged. Queue and preflight gain minimal holder/recipient/warehouse names and no-store headers; secrets, emails and full membership records are absent. All four discovery reads perform no business writes, claims or external effects. Typed malformed cash inputs now return sanitized 400 CASH_INPUT_INVALID rather than 500. Existing CASH_* operational errors remain distinct from CASH_OPERATION_CONFLICT; the frontend does not classify every 409 as identity conflict.

Existing mutation endpoints and locking/receipts remain authoritative and unchanged. The shared held-custody validator retains FOR UPDATE for execution and uses a non-write-lock read for recipient discovery. A database UNIQUE(collectionId,expectedEventId) already permits one offer per custody event: no new pagination scheme or schema was needed. A new-ID second offer is rejected without mutation (the existing database rejection currently maps to sanitized 500); the workspace prevents offering again while that offer is pending. Only the original matching receipt retry is supported. No offer cancellation/replacement policy is introduced.

Deploy these additive reads before the frontend. No migration, permission, supplemental profile, base role/scope, accounting or obligation policy changed. Rolling back UI does not relax backend authorization. Stop obsolete cash clients; their holder-ID/Float mutation contract is contained, not adapted or automatically replayed. Preserve stored legacy requests for reconciliation.
