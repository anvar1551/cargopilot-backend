# Durable integration webhook acknowledgement

Current enforced behavior: signature verification still precedes persistence. Duplicate checks receive the configured provider/company/domain/environment and SHA256 of the exact verified raw body, never request ownership fields. A duplicate must have matching verified raw identity, current active provider/company/tenant, matching normalized ownership metadata and a bound pending canonical record. `hasProcessed` remains an internal compatibility name: it now means durable acceptance, not successful domain processing. Protected content/errors are not retrieved by this receipt check.

Raw-only or normalized-only persistence throws sanitized `503 WEBHOOK_INGRESS_INCOMPLETE` before acknowledging success. A racing unique insert rechecks durable completeness instead of treating every P2002 as a duplicate. Mismatched body/ownership returns409; inactive current ownership denies. A gateway without pending persistence cannot accept verified ingress. Normal accepted202 and complete duplicate200 shapes remain. Persistence exceptions return sanitized rejection responses, not database details or false acceptance. No immediate retry or provider replay was introduced.

Partial failures are contained, not repaired: raw, normalized and pending writes are still separate transactions. Existing incomplete receipts remain unavailable until atomic ingress/reconciliation is implemented; repeated delivery will not silently overwrite or delete them. Provider retry schedules and delivery guarantees are unverified and must not be invented. A503 indicates that this request was not acknowledged; it does not prove a remote provider will retry. The receipt establishes complete persistence, not booking/lifecycle authorization or successful business application; those remain under the existing executor. Historical payload/ownership certification is not claimed.
