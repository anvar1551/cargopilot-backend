# Typed payment reservation authority plan

Baseline b3673d19e714108109b232ba849e544ab58b096d. This is a dependency-ready technical slice, not an approval-policy decision. Implemented source/constraint slice; exact evidence and compatibility are recorded in Payment_Reservation_Authority.md.

Confirmed gap: PaymentIntent currently has company/order/provider/config/environment/exact amountMinor/currency and durable company/idempotency uniqueness. Migration20261002210000_payment_source_relationships already binds order/company and configured provider/company/provider/environment. payment-creation.ts reloads the authorized tenant/order/issued invoice/active entity, derives exact minor units, stores invoiceId/legalEntityId/request and authority digests only in metadataJson, and only the winning reservation calls Stripe. payment-webhook.ts reloads current roots and exact invoice authority and commits signature-bound deduplication/ledger/order results transactionally. These application protections are real, but they do not provide typed intent-to-invoice/tenant/entity database relationships or immutable accepted monetary/request source fields. Do not replace or duplicate existing order/provider FKs, signature verification, callback admission, deduplication, order locks or uncertain-provider containment.

Bounded implementation:

1. Expand PaymentIntent with nullable reservation tenant, invoice, legal entity, acceptedAt and fixed request/authority hashes. Use existing amountMinor/currency as the immutable monetary snapshot. Names must make reservation acceptance distinct from pricing/invoice/accounting approval. Inspect all current intent writes before deciding the exact immutable field tuple. No historical JSON inference/backfill or default tenant/acceptance.
2. Add only the missing compound targets: Invoice's exact tenant/id/order/company/currency source (the existing tenant/order/company target does not by itself bind a selected invoiceId). Reuse Order tenant/id/ownerOrgId and FinanceLegalEntity id/tenant/company targets. New NOT VALID FKs bind populated intent roots/source; completeness and positive exact-money/hash checks prohibit partial bridges. Accepted owner/order/config/provider/environment/money/currency/key/source/hashes/time must be immutable; legacy null receipts cannot be adopted by update. Status and legitimate booking/attempt/result transitions remain permitted. Historical certification stays open.
3. Derive all fields inside the existing authorized locked reservation transaction, with explicit field projection. Client metadata, IDs and Redis/webhook payloads cannot establish acceptance. Every matching retry reloads current eligibility and current invoice/entity, requires the exact accepted typed tuple/hashes and returns only the established projection. Missing legacy receipts require reconciliation, never silent adoption or a new charge. Different order/request/source/money conflicts reject before provider work.
4. Extend callback's narrow intent select and source assertion to require that same typed receipt, current immutable source hash and exact money. Preserve provider authentication, accepted external booking, supported lifecycle, duplicate fingerprint and ledger/order transaction. Existing invoice status alone must not be described as approved pricing/FX. Keep new invoice issuance, unsupported providers, cash allocation, refunds/checker and recovery contained.

Exact implementation consumers: prisma/models/payments.prisma; inverse relation only in prisma/models/finance.prisma (and Order inverse model only if needed); one new migration; payment-creation.ts; payment-webhook.ts. Recheck all located PaymentIntent writes for permitted post-reservation updates, not a broad audit. Focused tests: payment-authority.test.ts, payment-reservation-postgres.integration.test.ts, payment-callback-postgres.integration.test.ts and the directly affected callback unit/HTTP fixture consumers. Reuse current synthetically owned persistence adapter and guard; no new infrastructure harness.

Acceptance evidence: authorized exact reservation and identical retries; concurrent identical/different-order-key requests produce one reservation and one mocked provider attempt; foreign tenant/company/invoice/entity and mismatched currency inserts/updates reject; partial/legacy/unaccepted/conflicting receipts deny current retry/callback; accepted tuple mutation rejects; valid status/booking transitions still work; injected source/reservation/callback transaction failures leave intent/attempt/receipt/ledger/order/outbox business state unchanged. Use one newly owned full current migration-chain PostgreSQL run for compatible reservation, callback and constraint/concurrency cases. Assertions must inspect exact money, final rows and no duplicate downstream effects, not just statuses. Provider I/O remains mocked/offline; do not claim exactly-once or live transport.

Rollout: stop old checkout writers and callback processors, apply additive migration, deploy matching new writers/readers/consumers, then selectively enable only previously supported workflows. Mixed writers could create legacy unaccepted rows and contact providers, so mixed rollout is unsafe. Do not restore metadata-only fallback on rollback; keep affected operations contained. Old accepted-intent metadata cannot be certified automatically. Existing safe reads may remain available through current selected-context projections. Document the resulting legacy checkout/callback incompatibility; clients remain deferred. All prior NOT VALID/null/RLS/native infrastructure and pricing/FX/accounting/checker/recovery blockers remain.
