# Import downstream recovery — unimplemented plan

Source reviewed: orders-core/import/order-import.ts, write/create-order.ts, repo/order-write.repo.ts, orders-legs/pricing.ts, label/order-label.ts and integrations-core/application/outbox-dispatcher.ts. This document records the current contract and proposed next work. It implements no replay, reconciliation, cancellation or new worker.

## Current durable sources and boundaries

| Stage | Durable source/current state | Supported safe retry | Reconciliation or missing mechanism |
|---|---|---|---|
| Order row | Context-bound OrderCreationIntent + ordinal OrderCreationReceipt + Order/parcel/cash/Tracking/analytics transaction | Same operationId, normalized full ordered batch and fresh authorization; completed rows return existing orders, only missing ordinals create | Batch is sequential partial success, not whole-batch atomic. A receipt proves row commit, not downstream completion. |
| Pricing/leg seed | Existing Order monetary estimate and PricingComponent/OrderLeg rows; system service-charge reference keys | No automatic import retry of a completed row; seed has its own transaction/ownership checks | Seed is separate best-effort after row commit; failure logs a bounded code/order ID and import continues. No durable per-row accepted seed input/version/completion receipt. Reinvoking current code can update estimates from current configuration and enqueue another analytics event; reference keys alone do not prove immutable recovery authority. Never treat rule markers as financial acceptance. |
| Label enqueue/execution | OrderLabelJob accepted ownership/capability, attempt/lock/status; parcel label attachments | Existing bounded eligible pending/failed claims with attempt fencing and authoritative ownership; already-labelled parcels skipped | Enqueue occurs after row commit. Enqueue failure may throw (or configured inline fallback); async render failure only logs; sync render failure throws. Retry of completed row skips enqueue/render entirely. No atomic row-to-label acceptance bridge; no autonomous stale processing-lease recovery. Fallback/worker overlap and storage/attachment crash require reconciliation, not resetting accepted jobs. |
| Carrier work | Accepted carrier OutboxEvent, attempt/admission and canonical durable result; authoritative order/leg/provider | Existing accepted tracking/result application and deduplication; mutating dispatch at most one durable admission | CSV import does **not** call autoBookCarrierForOrder. Normal order creation does. Later carrier operations require their own accepted ownership/capability. Prior admission/attempt/uncertain outcome holds mutations; never clear executionStartedAt or synthesize a new provider request to replay. Result persistence/canonical publication repair and provider evidence remain unresolved. |

Import downstreamRecoveryRequired is a conservative replayedRows > 0 hint, not a durable diagnosis. It may be true after complete downstream success or false despite a swallowed seed failure. Neither response status nor this flag authorizes repair. A failure after receipt can leave later ordinals missing; retry safely resumes those missing rows but intentionally does not repeat earlier effects. Current PostgreSQL partial-row recovery/rollback evidence is reused; downstream providers/storage are not certified by it.

1. Add a selected-context, read-only recovery inventory tied to accepted intent/ordinal/order. Reload scoped Order, pricing/leg rows, label jobs/attachments and existing carrier records; project only relevant state. Distinguish absent acceptance, known failure, processing, confirmed result and uncertain external outcome. Do not derive ownership from logs or userId alone.
2. Define a durable immutable post-commit work acceptance/receipt contract before enabling mutation: order/source/operation/version identity, frozen server-controlled inputs, compound ownership, one acceptance with business transaction, bounded fenced execution and transactional result publication. Stop at a reviewed plan until source-specific authority is known; do not invent a generic worker or use order receipt as downstream capability.
3. Only resume work whose authority, original inputs and known absence of completed effects are provable. Preserve original records. Label storage requires object/attachment reconciliation; pricing regeneration requires an explicit approved choice between original frozen estimate and repricing; carrier ambiguity requires provider-specific outcome evidence. No blind replay, overwrite or manual receipt reset.

Required business decisions: permitted repricing and quote expiry after partial commit; authorized reconciliation/checker and cancellation/reacceptance actors; treatment of partial label/storage and uncertain carrier outcomes. Existing retention and owner-company recipient policy remain unchanged. New invoice/finance approval and FX policy remain separately blocked.

Completion criteria for later implementation: current scoped state inventory without writes; immutable accepted original operation; concurrent repair produces one result/event; fresh authorization and ownership; no provider replay after uncertainty; injected transaction/storage/publication failures leave distinguishable recoverable state. Validate each chosen mechanism with focused disposable PostgreSQL concurrency/rollback and mocked storage/provider boundaries, then separately authorized real transport checks.
