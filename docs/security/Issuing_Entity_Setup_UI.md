## Implemented contracts

- New GET /api/auth/issuing-entity-setup?view=authority|proposals&kind=proposer|checker&limit=1..50&cursor=... is authenticated/private/no-store. Existing owner-accepted issuing-entity-setup.v1 and explicit selected-company scope are required; no FinanceLegalEntity prerequisite. Authority returns company display name, current supported currency registry, null reporting restriction and minimal existing publication. No operator keys, email addresses, credentials, unrelated roles or grants.
- Proposal pages use bounded UUID keyset pagination and a selected-user membership/tenant/company/kind-bound cursor. Proposers see only their own selected-membership records; checkers see owned company records. Exact normalized configuration, content hash, proposer User identity/name, proposal reason/time, independence and decision/reason/time are explicit projections. Reads preserve the existing setup reference-lock/company-fence/authority-lock order, never appoint authority or publish.
- Existing POST proposals/decisions and GET proposal/:id remain authoritative. No mutation policy, schema, permission, ceiling or profile changes. A demonstrated foreign-proposal 404 was accidentally mapped to 500; HTTP now preserves only ENTITY_SETUP_PROPOSAL_NOT_FOUND's 404, without changing other delegation error mapping.
- Frontend /dashboard/manager/entity-setup adds permission-aware navigation and proposer/checker views. Currency, month and timezone start blank and require explicit input. Reporting currency is null. Decisions require inspected exact proposal, a separate human, explicit approve/reject choice and reason. Publication is read-only; historical authorized retries remain available even after configuration exists.
- cp_entity_setup_v1 stores non-secret immutable mutation intents partitioned by API origin and exact authenticated context/kind. Installed Web Locks, persist/read-back before send, stable operationId/normalized content, no automatic replay, and auth-epoch guards protect explicit retries/reloads and late responses. Decisions persist inspected configuration/hash; refreshed selectors cannot substitute pending intent. Mismatched receipts stay uncertain. Only confirmed intents may be finished. Unconfirmed reconciliation/abandon remains unavailable.
