# Callback admission and PostgreSQL deadlines

Current enforced behavior: at most eight active callback operations per process, no application waiting queue, fail-fast503 PAYMENT_CALLBACK_CAPACITY before database factory/resolution, parsing, credentials or provider work. Slots remain held until the awaited operation settles; neither HTTP timeout/disconnect nor a Promise.race frees them or replays work. Only the covered Stripe path reaches database resolution; raw bytes remain bounded64KiB. Signature, source/money graph, durable dedup, business locks/transactions and commit-before-acknowledgement are unchanged.

Callbacks now lazily use a separate PostgreSQL pool: max8, native driver acquisition1000ms, default statement3000ms/lock1000ms/idle-in-transaction5000ms. Construction does not connect, load dotenv, start workers or seed. Existing configured DATABASE_URL is used only at runtime; no endpoint/credential was accessed by this task. Accelerate-only configuration cannot establish these PostgreSQL controls and returns sanitized503 without fallback. Fastify close releases the callback client/pool; idle pool errors are handled without logging driver/credential details. Non-callback application pool behavior is unchanged.

Preflight booking/ownership reads now execute in a read-only transaction with statement3s/lock1s, Prisma acquisition2s/transaction5s. The driver deadline precedes Prisma acquisition: equal1s limits reproduced a leftover queued driver waiter after Prisma returned. Increasing the outer acquisition limit corrected that race without weakening the zero-waiter assertion. Business transaction retains acquisition2s/transaction10s and statement5s/lock3s. Verification remains outside business transactions; covered Stripe verification is local SDK cryptography, not a provider HTTP operation. No immediate retries, uncertain provider replay or invented provider delivery schedule. Capacity returns503 with no receipt; unexpected database failures remain safe500, never an acknowledgement of processing. Identical later authorized provider retries still resolve the durable receipt after source/signature verification.

Limits: this is not real network-partition/TCP-blackhole or multi-process infrastructure evidence. Transaction deadlines are not an atomicity claim across PostgreSQL and external systems. Idle connections intentionally remain pooled; no claim all connections close after each request. Pool bounds limit physical connections/pending work, while admission is per process rather than per tenant; fair allocation across tenants/replicas and deployment sizing remain outstanding.
