# Payment-run authorization and approval containment

Current enforced behavior: existing list/detail HTTP, service and repository boundaries require fresh selected tenant/company membership, `finance.treasury.read` and explicit stored company scope. Active tenant/company/legal entity is repeated at reads. Bank, payable and allocation ownership must agree with that entity. Null/inactive ownership is hidden; foreign details and cursors return404. Status and bounded page inputs are allowlisted; date/id keyset cursors use the same selected ownership/status predicates.

Minimal projections preserve exact stored Decimal amount/FX values, currency, workflow dates, masked bank display data and owned line counts. Raw metadata/hash/idempotency/bank-reference and actor fields are omitted. Details are capped at1000 lines, rejecting overflow rather than presenting truncated financial data. Details validate currency, carrier snapshots and allocation-to-payable pairing. Lists validate entity ownership and count scoped child rows; they do not certify all same-entity financial snapshot relationships. No reads create configuration or change financial state. Revocation concurrent with fresh checks remains a timing boundary.

All five mutations (create, submit, approve, reject, execute) require fresh action-specific permission, explicit company scope and matching selected actor/company at service and repository. They deny409 `FINANCE_PAYMENT_RUN_ACCEPTANCE_REQUIRED` before protected lookup, calculations, transaction, reservations, numbering, source events, audit or external effects. Caller amounts/FX, persisted approved status, `policy.override`, supplied checker/approval flags and old idempotency receipts cannot restore acceptance. HTTP approval/execution no longer generates override flags; normal request contracts remain parsed but mutations are unavailable. The former service-level override path is removed. Existing records are neither deleted nor rewritten.

Restoration requires authoritative accepted payable basis, approved accounting/FX policy, immutable accepted payment intent, independent checker eligibility and separate maker/checker/executor rules, plus cancellation/rejection/reacceptance and uncertain execution/recovery policy. Actor separation cannot be bypassed by overlapping permissions or a generic override. Read DTOs are not a financial execution authority; deleting the guard is not a safe restoration. Existing private transaction bodies/leases are preserved behind containment, not claimed validated as restored concurrency or exactly-once external delivery.

Compatibility: envelopes/event names remain unchanged; omitted internal fields, strict query inputs and unavailable mutations require later client adaptation. Frontend/driver work is deferred. Migration 20261002130000_payment_run_reference_ownership now adds compound bank/run/payable/entity targets and exact allocation-to-line/payable/entity constraints. Nullable line/allocation bridges are required on new or updated rows by NOT VALID checks. Private writers derive bridges from the authoritative entity; allocation projection reloads active ownership and executed parent/source/currency/FX relationships. Execution acceptance remains contained. No historical mapping or financial-state rewrite. Untouched historical null bridges still bypass storage equality but are hidden by reads; untouched conflicting references remain uncertified. NOT VALID foreign keys protect new/changed references, not every unrelated update to old foreign keys. Compound equality does not prove accepted financial basis or legal classification.
