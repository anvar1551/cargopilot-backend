# Typed immutable payment reservation authority

Current enforced behavior: checkout derives seven reservation fields from the current authorized selected membership, locked order, issued invoice and active owning finance entity. Three new compound FKs bind tenant/order/company, invoice tenant/id/order/company/currency and entity id/tenant/company. Existing order/provider FKs and company/idempotency uniqueness are retained. Exact bigint minor units, invoice issued time, request hash and authority hash are stored under the source transaction; this structural reservation is not independent pricing, FX or accounting approval.

Matching retries still reload permission, selected membership/object scope, current invoice/entity and provider configuration. They require the populated typed source plus existing server metadata digest; legacy/missing authority returns reconciliation-required. Conflicting content or source rejects before a provider operation. Callback's existing verified Stripe booking, current root, exact amount/currency and transactional deduplication controls now also require the typed source. No caller or queue field creates authority, and receipt possession grants no access. New invoice issuance, unsupported providers, cash allocation, refund/checker and unapproved finance posting remain contained.

Database integrity: the new NOT VALID completeness check permits either seven empty legacy fields or all populated fields with positive exact money and bounded lowercase hashes. It prevents partial bridges on new/changed rows. Accepted owner, source, exact amount/currency, provider/config/environment, idempotency key, server metadata and acceptance/issuance times cannot change. Accepted rows cannot be deleted, and truncation is blocked. Legacy rows cannot be adopted by update. Status, provider booking result and permitted attempt/ledger transitions remain controlled by existing application workflows. Privileged DB writes are not application authorization; RLS/DB-role control and historical certification remain unresolved. Nullable legacy rows still exist and are not certified by this expansion.

Compatibility/rollout: stop old checkout writers and callback processors, apply the additive migration, deploy matching writers/readers, then selectively enable only previously supported workflows. Keep old finance publishers stopped until the earlier finance-outbox rollout is complete; this slice does not change or enable their accounting policy. Mixed old writers could contact providers for reservations the new callback refuses, so mixed rollout is unsafe. Existing unaccepted reservations require explicit reconciliation, never JSON backfill, a fresh idempotency key or blind provider replay. Public successful response shapes and request IDs are unchanged; strict request schemas already reject caller authority fields. New currency/source FKs and accepted-row deletion restrictions may reject formerly permitted configuration/data cleanup. Rollback must preserve enforcement or disable affected checkout/callback operations.

Recovery: reservation commits before provider initiation. Only its creator dispatches; a matching reservation retry does not call the provider again, including after an uncertain external outcome. Existing attempt/result persistence follows in its own transaction. PostgreSQL cannot atomically commit with provider I/O; a crash/timeout remains reconciliation-required. No exactly-once transport, completed recovery tooling or approved accounting claim is made. Current authorization/state changes after the final read remain a timing boundary.
