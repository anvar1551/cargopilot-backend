# Callback reference lookup indexes

Migration20261002220000 adds two non-unique btree indexes on PaymentIntent: provider/providerInvoiceId and provider/providerPaymentId, with matching explicit Prisma names. Callback ingress cannot use request tenant/company as lookup authority; the stored external reference is resolved first, then the configured provider and complete authoritative ownership graph. Earlier company-leading indexes do not support that initial provider-reference predicate. This is a lookup-cost dependency, not an authorization grant. No unique/global booking assumption, default tenant, source rewrite or callback execution change is introduced. Ambiguous results still reject; existing take2/current graph/signature/exact-money/transactional receipt controls are unchanged.

Offline Prisma WASM syntax validation passed with the datasource-free temporary config. Manual selected index names/columns/order/non-unique properties match SQL; not complete schema-to-SQL semantic equivalence. Two focused disposable PostgreSQL cases apply the full86migration chain and check valid/non-unique indexes, planner eligibility with a bounded2000row synthetic distribution for both exact callback predicates, and real callback rejection of shared session/payment references with unchanged business snapshots. SET LOCAL enable_seqscan=off is confined to a rolled-back test transaction: eligibility does not establish production planner choice, performance under scale or latency/backpressure. No generated client is required for index-only schema additions; dist and application code remain unchanged.

Outstanding, not solved by indexes: bounded preflight DB admission/query deadlines and pending-work lifecycle, provider/infrastructure retry guarantees, independent immutable invoice/entity/configuration acceptance, exact cash allocation/checker/FX/accounting/recovery policies, unsupported providers, historical/null certification and all previous release blockers. The normal CREATE INDEX migration can block table writes while building on a populated deployment; deployment needs explicit approval and a reviewed lock/online-index strategy. No existing database was inspected or migrated. Rollback may drop only these optional performance indexes under a separately approved deployment procedure; it must not restore unsafe callback authority.
