# Provider configuration journal and atomic publication foundation

Current enforced foundation: IntegrationProviderConfigurationVersion is both an immutable non-financial configuration snapshot and durable actor/action receipt. It stores explicit scalar fields, context/membership identifiers, an operation identity and normalized intent digest; no plaintext/ciphertext credential values, arbitrary request metadata or headers. Tenant/company, provider domain/code/environment, actor company/tenant bridges and optional immutable secret ownership use existing compound targets. New rows are fully constrained; existing providers begin at revision0 with no acceptance, not an inferred historical version.

publishIntegrationProviderConfigurationForActor is a new backend-only service, not connected to HTTP configuration or rotation routes. It publishes the current authoritative scalar configuration and optionally an already existing immutable owned secret identifier. Fresh selected active membership, explicit company scope and manage permission are mandatory, plus rotateSecret permission for an explicit credential pointer. Financial domain is derived from the provider and denied pending independent approval. It accepts no ownership, status, monetary or secret-value fields. It does not create/encrypt credentials, contact providers, change retirement state, reaccept jobs or impersonate workers.

Durability: tenant/operation advisory lock precedes provider row lock; current revision and pointer are compared at the actual scoped update. Server allocates the next configuration revision. One transaction creates the action/version and publishes the pointer. Matching authorized retries return the original minimal receipt; changed actor/context/provider/revision/secret intent conflicts. Cross-provider operation reuse is serialized, not a read-then-create claim. Database uniqueness supplements locks. Journal update/delete/truncate is blocked. Provider snapshot/pointer triggers deny unjournaled rewrites and clearing acceptance. A deferred insert constraint prevents a receipt committing without its matching pointer publication; only one publication per provider per transaction is supported. A retry still proves current permission and ownership. Revocation between membership read and commit remains a timing boundary; immediate distributed revocation is not claimed.

Compatibility and migration: additive new table and revision/pointer fields, no backfill, no old migration edit, no existing service access. Existing credential-owner/append-only guards are retained. Both-null credential/configuration ownership remains intentionally unconfigured; journal tenant/membership fields are non-null. Existing HTTP POST/status/delete/rotation responses remain contained409; clients are deferred and no new endpoint is invented. Published provider fields become frozen to the current journal snapshot until a new atomic publication; arbitrary field updates must not bypass this. Safe rollback retains guards or disables affected operations. Prisma cannot express the CHECKs/triggers; selected source/SQL tuple review is not full semantic equivalence.
