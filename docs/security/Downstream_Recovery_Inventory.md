## Current contract and enforcement

GET /api/orders/:id/downstream-recovery?section=creation|pricing|labels|carrier&limit=25&cursor=UUID. Default section is creation. Other sections use ascending UUID seek pagination, limit 1–50 (default 25), one look-ahead row and nextCursor; creation is a single receipt and rejects cursors. A foreign cursor is only a position within the already scoped query, never a global record lookup. Clients must fetch each required section; pages are not a single cross-request snapshot.

Uses fresh requireAuthorizedOrder(shipment.view), requires the owning company to equal the selected company, then applies the existing membership-only order-scope helper to the actual parent and related predicates. This is an operational owner-company diagnostic: delegated dispatch visibility and user-global customer/warehouse links alone do not grant it. A PostgreSQL negative case demonstrated that the general compatibility helper can retain user-global access after explicit scope removal; the new inventory uses buildMembershipOrderScopeWhere instead. Other endpoints/policies were not changed. Missing context, removed permission/scope, tenant-null parent and foreign company/tenant fail closed. Authorization has the existing final-read timing boundary; no atomic concurrent revocation claim.

Each request runs in a bounded REPEATABLE READ / READ ONLY transaction, with 5-second statement timeout, 2-second admission wait and 10-second transaction timeout. Commands only set transaction characteristics; no business writes, claims, jobs, cache invalidations, signed URLs, storage or provider calls. Related reads retain parent ownership and explicit object-scope predicates. No schema/dependency/client change.

## Proposed next implementation: repair missing canonical publication only

Not implemented. Source gap: a carrier delivery result and the canonical enqueue occur separately; a crash may leave a durable successful accepted result without its canonical application record.

- Authority: original accepted IntegrationOutbox, current active authoritative order/tenant/company/provider/leg, and latest IntegrationDeliveryAttempt whose attemptNo equals outbox.attemptCount, outcome is success and outbox is sent. Reuse loadAcceptedCarrierOperation and deriveCanonicalSource plus integrationCanonicalEventRepository.enqueue. The existing derivation reads stored request/response and finishedAt; Redis/UI cannot supply them. Limit the first implementation to existing supported sandbox create_shipment result publication. It must validate the persisted response through the existing supported contract before application.
- Safe retry is **publication**, never another provider request: missing canonical row with provable accepted successful result, or identical existing canonical result, preserves the original outboxId/source/attempt time and payload. Revalidate source ownership and acceptance every attempt. Do not reset attempts, executionStartedAt, statuses or original IDs. A failed/pending/uncertain transport, missing/mismatched response, unaccepted legacy source, suspended owner or conflicting canonical identity remains held.
- Concurrency: reuse database source/outbox uniqueness and source locking; concurrent publication returns one identical canonical record, rejects conflicts. Existing canonical application retains its own atomic lifecycle/deduplication rules and scopes. No human membership impersonation, generic execution bypass or provider network call.
- Rollback/crash: failure before publication commit leaves the original result unchanged and repairable. Unknown publication commit retries the same source identity and reads the existing validated record. Failure/uncertainty in later lifecycle application remains separate; never modify a processed event or fabricate another business transition.
- Completion: bounded authoritative missing-publication selection; one canonical event and one permitted application/tracking/outbox result under competing repair/application; publication and application rollback/crash tests; conflict/revoked-owner/legacy/invalid-response cases produce no business effects; assert zero provider/storage calls throughout. Use focused disposable PostgreSQL uniqueness/concurrency/rollback evidence and reuse unchanged provider tests. No exactly-once external claim.

No new accounting or cancellation business decision is needed to publish an already accepted, durably successful supported result under the existing capability. Reacceptance, cancellation, uncertain external outcomes and unsupported providers remain blocked by their existing decisions/contracts; this proposal does not repair those paths. If source inspection cannot prove the recorded success/response contract for a provider, keep that provider contained.
