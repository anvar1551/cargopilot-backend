# Atomic dispatch notification persistence plan

Status: **Implemented within the bounded covered dispatch paths.** See [Atomic_Dispatch_Notifications.md](Atomic_Dispatch_Notifications.md) for current behavior, evidence, rollout and limitations. Realtime transport remains best-effort.

The original plan below is historical; its baseline “no implementation started” statement is superseded by the implementation report.

Baseline f9ddd46fb81e74005a4bfbbc34124b79182c1e8b; no implementation started. Confirmed bounded gap: operations/order-status.ts commits current-authorized conditional Order changes, Tracking and accepted analytics facts together. operations/tasks.ts then fire-and-forgets emitDriverNotification and suppresses failure. realtimeHub.ts separately resolves current owner-company/assigned-driver context and calls createUserNotification. The latter's populated tenant/company/order/recipient compound constraints prevent foreign links, but its separate create can be lost after a crash or duplicated on repeated emission. Existing notification reads/realtime revocation are not atomic source acceptance. Analytics payload contains assignment information but its generic order-event capability is not a dedicated notification authority; do not treat payload or free-form Tracking.note as permission.

Smallest proposed slice: persist eligible UserNotification records inside the three covered dispatch transactions, using the Tracking row created by that transaction as durable source identity. Inspect/reuse any existing Tracking id/order target first; add only a missing compound source target/FK and nullable accepted dispatch-source bridge/uniqueness if needed. Existing notification owner and exact recipient membership constraints remain. Derive order owner/tenant, assigned recipient, current active tenant/company/user membership and drivers.telemetry eligibility through trusted transaction reads; no human impersonation or generic context bypass. Preserve the current owner-company recipient policy. If selected assigned-company context does not establish an eligible owner-company recipient, suppress this notification rather than infer ownership, select a membership or extend cross-company delivery. No historical adoption.

Keep templates minimal/server-controlled (order number/status/time); no request note, arbitrary content, financial payload or raw actor role. Notification source/recipient/owner must not be retargeted after acceptance; readAt remains mutable through current recipient-authorized operations. No-op assignments and matching accepted source retries must not create new rows. A real notification persistence failure rolls back related Order/Tracking/analytics business writes; explicitly document that stronger failure behavior. Ineligible/ambiguous recipients retain safe suppression. Inspect existing retention and deletion rules before deciding immutable receipt/deletion constraints; do not invent a retention policy or silently prevent the approved own-record retention workflow.

After commit, tasks/realtime should deliver existing persisted IDs through narrowly defined reload/current recipient/order-context checks, without another create. Realtime remains best-effort, not exactly-once transport; the durable own-context notification list survives a missed socket delivery. No new infrastructure worker is necessary merely to make the existing notification row atomic. If a different durable-delivery requirement is demonstrated, record it separately rather than build a generic replay worker. Existing initiating-user permission checks are source acceptance, not an implicit continued-login condition for reloading accepted notifications; current recipient eligibility still denies delivery after revocation. Final-read revocation races remain.

Files to trace/edit: order-status.ts, tasks.ts, notificationService.ts and realtimeHub.ts; notifications/orders Prisma models only as needed, one new migration if required; current dispatch/notification/realtime tests and actual disposable dispatch concurrency/rollback adapter. Inspect all alternate callers before changing create/delivery contracts. Preserve cash, manual status override, driver classification/delegation, pricing/FX, broader analytics and clients.

Acceptance: authorized same-company operation creates one Tracking/owned notification/analytics fact atomically; same user across tenants/companies reaches only the accepted eligible recipient context; missing/null/foreign/wrong source/recipient and insufficient permission cannot create or deliver; duplicate/no-op/concurrent operations do not duplicate notification rows; second-row notification failure rolls back the covered batch with existing documented batch semantics; parent/current-recipient revocation and stale source delivery deny without new business writes; no socket fallback or storage/provider effect. Combine affected PostgreSQL cases in one exclusively owned full current chain run, assert exact records/counts and cleanup. Mock Socket.IO evidence must remain separate from actual database evidence. No new policy or existing service access.
